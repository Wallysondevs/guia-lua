Lua debug

Quando um programa faz alguma coisa estranha, a primeira pergunta é sempre: onde ele estava e o que ele tinha na mão naquela hora? A biblioteca debug ("depuração", o trabalho de achar e tirar defeitos de um programa) deixa o próprio programa responder: ela mostra o caminho das chamadas até a linha atual, diz o nome e a linha de cada função, lista as variáveis locais e até pendura um "gancho" que roda a cada linha. Esta aula apresenta as quatro funções mais úteis dela. As técnicas de procurar defeito ficam na próxima aula, Depurando um Programa.

Você vai aprender
  • debug.traceback: o "rastro" das chamadas, o mesmo que aparece embaixo de uma mensagem de erro.
  • debug.getinfo: a linha atual, o nome da função e o arquivo, de você mesmo ou de quem chamou.
  • debug.getlocal: os nomes e os valores das variáveis locais de uma função.
  • debug.sethook: um gancho chamado a cada linha, a cada chamada de função ou a cada tantas instruções.
  • Os níveis da pilha (1, 2, 3…), a ideia que todas essas funções usam.
  • Por que a biblioteca debug é para depurar, e não para a lógica do programa.

Os programas desta aula rodaram no Lua 5.5 da máquina da Ana (usuária ana, computador notebook), com lua arquivo.lua. Vale conhecer antes Funções, Lendo uma Mensagem de Erro e xpcall e debug.traceback.

A ideia: a pilha de pratos

Na cozinha da padaria, cada pedido vira um prato na pilha. O padeiro está fazendo um bolo (prato de baixo). No meio, precisa de cobertura: põe o prato "cobertura" em cima e vai fazer a cobertura. Para a cobertura, precisa derreter chocolate: mais um prato em cima. Quando o chocolate fica pronto, o prato de cima sai e ele volta para a cobertura; quando a cobertura fica pronta, volta para o bolo.

Um programa faz igual com as funções: o programa principal chama boletim, que chama calcular_media. Cada chamada que ainda não terminou é um prato na pilha de chamadas (em inglês, call stack). A biblioteca debug conta os pratos de cima para baixo, por nível:

NívelQuem é
0a própria função do debug que você chamou (getinfo, por exemplo)
1a função onde está a linha que chamou o debug: "eu"
2quem chamou essa função: "quem me chamou"
3, 4…e assim por diante, até o programa principal (o main chunk)

1. O caminho até aqui: debug.traceback

debug.traceback(mensagem) devolve um texto com a mensagem e, embaixo, a pilha de chamadas naquele momento. É o mesmo stack traceback: que o Lua mostra quando dá erro, só que sem erro nenhum: o programa continua.

local function calcular_media(notas)
  print(debug.traceback("Onde estou?"))
  local soma = 0
  for _, nota in ipairs(notas) do soma = soma + nota end
  return soma / #notas
end

local function boletim(aluno)
  local media = calcular_media(aluno.notas)
  print(aluno.nome .. ": média " .. media)
end

boletim({ nome = "Ana", notas = { 8, 9 } })

$ lua rastro.lua
Onde estou?
stack traceback:

	rastro.lua:9: in local 'boletim'
	rastro.lua:13: in main chunk
	[C]: in ?
Ana: média 8.5

Leia de cima para baixo: é a pilha de pratos, do de cima (o mais recente) para o de baixo.

Onde estou?
A mensagem que você passou, na primeira linha.
stack traceback:
"Rastro da pilha": daqui para baixo vem a lista de chamadas.

Agora o programa está na linha 2, dentro de calcular_media. O upvalue diz como o Lua achou esse nome: boletim usa a variável local calcular_media, que foi criada fora dela (uma variável "de fora" usada dentro de uma função é um upvalue; veja Closures).

Ana: média 8.5
Depois do rastro, o programa seguiu normalmente.

Outras palavras que aparecem no lugar de upvalue e local: global (uma função global, como print), field (um campo de tabela, como string.pack), method (chamada com :) e function <rastro.lua:1> quando o Lua não sabe o nome e só mostra onde a função começa.

O nível de onde começar

Um segundo argumento diz de qual nível o rastro começa. Com 2, ele pula a função atual e começa em quem a chamou, útil numa função "de verificação" que quer apontar o culpado:

local function verificar(nota)
  if nota > 10 then
    print(debug.traceback("nota inválida: " .. nota, 2))
  end
end

local function lancar(nota)
  verificar(nota)
end

lancar(12)

$ lua nivel.lua
nota inválida: 12
stack traceback:
	nivel.lua:8: in local 'lancar'
	nivel.lua:11: in main chunk
	[C]: in ?

A linha de verificar não aparece: o rastro começa em lancar, linha 8, que foi quem mandou a nota errada.

O uso mais comum: junto com o xpcall

Quando você captura um erro com pcall, a mensagem chega sem o rastro. Com xpcall(funcao, debug.traceback), o Lua chama o debug.traceback na hora do erro, e você recebe a mensagem com o rastro completo, sem o programa parar. Isso tem aula própria: xpcall e debug.traceback.

Curiosidade: o prato que some (chamada de cauda)

Troque o boletim por uma versão que faz return calcular_media(aluno.notas):

local function calcular_media(notas)
  print(debug.traceback("Onde estou?"))
  return 0
end

local function boletim(aluno)
  return calcular_media(aluno.notas)
end

boletim({ nome = "Ana", notas = { 8, 9 } })

$ lua cauda.lua
Onde estou?
stack traceback:
	cauda.lua:2: in function <cauda.lua:1>
	(...tail calls...)
	cauda.lua:10: in main chunk
	[C]: in ?

O boletim sumiu do rastro, e no lugar dele aparece (...tail calls...) ("chamadas de cauda"). Um return f(…) é uma chamada de cauda: o Lua tira o prato de boletim da pilha antes de chamar calcular_media, porque não há mais nada para fazer nele. Sem o prato, ele também perde o nome (por isso function <cauda.lua:1>). Não é defeito; só não se assuste quando vir isso num rastro.

2. Quem sou eu, onde estou: debug.getinfo

debug.getinfo(nivel) devolve uma tabela com informações sobre a função daquele nível:

local function quem_sou_eu()
  local info = debug.getinfo(1)
  print("linha atual:", info.currentline)
  print("nome:", info.name)
  print("arquivo:", info.short_src)
  print("source:", info.source)
  print("começa na linha:", info.linedefined)
  print("termina na linha:", info.lastlinedefined)
  print("tipo:", info.what)
  print("namewhat:", info.namewhat)
  print("nparams:", info.nparams)
end

Pedindo só uma parte

Um segundo argumento escolhe quais campos preencher, com letras: "l" = a linha atual, "n" = o nome, "S" = a fonte (arquivo, linhas, what), "u" = parâmetros. Pedir só o que precisa é mais rápido.

Quem me chamou? Nível 2

O uso mais prático do getinfo: uma função de "registro" (um log) que mostra de que linha ela foi chamada. Para isso, ela pergunta pelo nível 2, quem a chamou:

local function registrar(mensagem)
  local info = debug.getinfo(2, "Sl")
  print(string.format("[%s:%d] %s", info.short_src, info.currentline, mensagem))
end

local function vender(produto, quantidade)
  registrar("vendendo " .. quantidade .. " " .. produto)
end

registrar("começou")
vender("pão", 6)
registrar("terminou")

$ lua quem.lua
[quem.lua:10] começou
[quem.lua:7] vendendo 6 pão
[quem.lua:12] terminou

Cada mensagem saiu com o arquivo e a linha de quem chamou o registrar: as linhas 10 e 12 (programa principal) e a 7 (dentro de vender). Num programa grande, isso diz na hora de onde veio cada mensagem.

Missão: aqui o registrar pergunta pelo nível 1 e, por isso, toda mensagem sai com a linha 2 (a dele mesmo). Faça cada mensagem mostrar a linha de quem chamou.

Informação sobre uma função qualquer

No lugar do nível, dá para passar a própria função:

local function dobro(x)
  return x * 2
end
local info = debug.getinfo(dobro)
print(info.what, info.short_src, info.linedefined, info.lastlinedefined, info.nparams)
local p = debug.getinfo(print)
print(p.what, p.short_src, p.linedefined)
print(debug.getinfo(50))

$ lua infofunc.lua
Lua	infofunc.lua	1	3	1
C	[C]	-1
nil

A dobro é uma função Lua das linhas 1 a 3, com 1 parâmetro. O print é uma função em C: não tem arquivo ([C]) nem linha (-1). E um nível que não existe (não há 50 pratos na pilha) dá nil.

3. As variáveis locais: debug.getlocal

debug.getlocal(nivel, i) devolve o nome e o valor da variável local número i da função daquele nível (as variáveis contam na ordem em que foram declaradas, começando pelos parâmetros). Quando não há mais variáveis, devolve nil. Com um laço, dá para listar todas:

local function conta(preco, quantidade)
  local total = preco * quantidade
  local i = 1
  while true do
    local nome, valor = debug.getlocal(1, i)
    if not nome then break end
    print(i, nome, valor)
    i = i + 1
  end
  return total
end

conta(4.5, 3)

$ lua locais.lua
1	preco	4.5
2	quantidade	3
3	total	13.5
4	i	4

Os dois parâmetros vêm primeiro, depois total e o próprio i do laço. Repare que o i mostrou 4: na hora em que o getlocal leu a variável número 4, o i já valia 4. As variáveis nome e valor não aparecem porque são declaradas depois, dentro do laço, e o getlocal só conta as que já existem naquele ponto do código.

Isso fura a regra do local

Uma variável local deveria ser invisível fora da função. O getlocal (e o debug.setlocal, que até muda o valor) passa por cima dessa regra. O manual do Lua avisa: várias funções do debug violam garantias básicas da linguagem e algumas são lentas. Use para investigar um defeito, nunca como parte normal do programa.

4. O gancho: debug.sethook

debug.sethook(funcao, mascara) pendura um gancho (em inglês, hook): uma função sua que o Lua chama sozinho em certos momentos. A máscara diz quando:

MáscaraO gancho é chamado…O evento recebido
"l"a cada linha nova de código"line", e o número da linha
"c"a cada chamada de função"call" ou "tail call"
"r"a cada retorno de função"return"
"" e um número na cada n instruções da máquina do Lua"count"

Para tirar o gancho, chame debug.sethook() sem nada.

A cada linha

local function contar_linhas(evento, linha)
  print("  rodando a linha " .. linha)
end

local function soma(a, b)
  local s = a + b
  return s
end

debug.sethook(contar_linhas, "l")
local r = soma(2, 3)
print("resultado:", r)
debug.sethook()
print("gancho desligado")

$ lua gancho.lua
  rodando a linha 11
  rodando a linha 6
  rodando a linha 7
  rodando a linha 12
resultado:	5
  rodando a linha 13
gancho desligado

Dá para seguir o programa passo a passo: linha 11 (chama soma), linhas 6 e 7 (dentro de soma), linha 12 (o print), linha 13 (o debug.sethook() que desliga). O gancho é chamado antes de a linha rodar: por isso "rodando a linha 12" aparece antes de resultado: 5. Depois de desligado, a linha 14 rodou sem aviso.

A cada chamada

Dentro do gancho, o nível 2 do getinfo é a função que acabou de ser chamada (o nível 1 é o próprio gancho):

local function ao_chamar(evento)
  local info = debug.getinfo(2, "nS")
  if info.what == "Lua" then
    print(evento, info.name or "?", "linha " .. info.linedefined)
  end
end

local function quadrado(x) return x * x end
local function soma_quadrados(a, b) return quadrado(a) + quadrado(b) end

debug.sethook(ao_chamar, "c")
print(soma_quadrados(3, 4))
debug.sethook()

$ lua chamadas.lua
call	soma_quadrados	linha 9
call	quadrado	linha 8
call	quadrado	linha 8
25

O if info.what == "Lua" deixa de fora as funções em C (o print e o próprio debug.sethook, que também são chamadas). Sobram as três chamadas das funções do programa.

A cada tantas instruções: um freio de segurança

Com a máscara vazia e um número, o gancho roda a cada tantas instruções (os passinhos da máquina do Lua; uma linha pode ter vários). Um uso clássico é um "freio": parar um programa que está demorando demais, levantando um erro de dentro do gancho:

local limite = os.clock() + 1
debug.sethook(function ()
  if os.clock() > limite then
    error("demorou demais!")
  end
end, "", 100000)

local n = 0
while true do n = n + 1 end

$ lua freio.lua
lua: freio.lua:4: demorou demais!
stack traceback:
	[C]: in global 'error'
	freio.lua:4: in hook '?'
	freio.lua:9: in main chunk
	[C]: in ?

O while true da linha 9 nunca terminaria. A cada 100 000 instruções, o gancho olha o relógio (os.clock, o tempo de processador gasto; veja os.getenv, os.clock e os.exit) e, depois de 1 segundo, levanta o erro. No rastro aparece in hook '?': o erro nasceu dentro de um gancho. É assim que programas que rodam código de outras pessoas (o Lua dentro de um jogo, por exemplo) se protegem de laços infinitos.

Outras versões

A biblioteca debug existe em todas as versões. Os detalhes mudam: no Lua 5.1 e no LuaJIT, o rastro escreve in function 'calcular_media' em vez de in upvalue 'calcular_media', e a última linha é [C]: ? (5.1) ou [C]: at 0x… (LuaJIT, com um endereço). O campo nparams do getinfo não existe no 5.1 (lá ele dá nil; o LuaJIT tem). Veja as diferenças entre as versões.

Quando dá errado

"O nome saiu nil"

O name do getinfo é o nome pelo qual a função foi chamada, não um nome guardado nela. No programa principal ele é nil; numa chamada de cauda também; e a mesma função chamada por duas variáveis diferentes mostra dois nomes:

local info = debug.getinfo(1, "n")
print(info.name)
local t = {}
function t.salvar()
  print(debug.getinfo(1, "n").name, debug.getinfo(1, "n").namewhat)
end
t.salvar()
local f = t.salvar
f()

$ lua nomenil.lua
nil
salvar	field
f	local

Para mostrar um nome, use info.name or "?", como no exemplo das chamadas.

Missão final: quantas vezes a função foi chamada?

Missão: a função fib chama a si mesma (veja Recursão), e a Ana quer saber quantas vezes ela é chamada para calcular fib(10). O gancho de chamadas já está pendurado, mas não conta nada. Dentro dele, pegue o nome da função chamada com debug.getinfo(2, "n") e, se o nome for "fib", some 1 em chamadas.

local chamadas = 0

local function fib(n)
  if n < 2 then return n end
  return fib(n - 1) + fib(n - 2)
end

debug.sethook(function (evento)
  -- conte aqui as chamadas da fib
end, "c")
local resultado = fib(10)
debug.sethook()

print("fib(10) =", resultado)
print("fib foi chamada " .. chamadas .. " vezes")

local chamadas = 0

local function fib(n)
  if n < 2 then return n end
  return fib(n - 1) + fib(n - 2)
end

debug.sethook(function (evento)
  local info = debug.getinfo(2, "n")
  if info.name == "fib" then
    chamadas = chamadas + 1
  end
end, "c")
local resultado = fib(10)
debug.sethook()

print("fib(10) =", resultado)
print("fib foi chamada " .. chamadas .. " vezes")

No lab, a solução mostrou:

$ lua fib.lua
fib(10) =	55
fib foi chamada 177 vezes

177 chamadas para um resultado de 55: é por isso que essa fib fica lentíssima com números maiores. Medir com um gancho é o primeiro passo para descobrir onde um programa gasta o tempo.

Resumo

  • As funções do debug contam a pilha de chamadas por nível: 1 = a função atual, 2 = quem a chamou, e assim por diante.
  • debug.traceback(msg) devolve o rastro da pilha como texto, sem parar o programa; com xpcall, mostra o rastro de um erro.
  • debug.getinfo(nivel, "Sl") dá arquivo (short_src), linha (currentline), nome (name) e mais; com um nível que não existe, devolve nil.
  • debug.getlocal(nivel, i) lista as variáveis locais, na ordem em que foram declaradas.
  • debug.sethook(f, "l"), "c", "r" ou ("", n) pendura um gancho; debug.sethook() tira.
  • É uma biblioteca para investigar: lenta em partes e capaz de furar regras da linguagem. Na lógica do programa, não.
