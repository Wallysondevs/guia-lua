Lua __index e __newindex

Quando você lê uma chave que não existe numa tabela, o Lua responde nil. Quando você grava uma chave nova, ele simplesmente cria. Os metamétodos __index ("índice", em inglês) e __newindex ("índice novo") deixam você mudar essas duas respostas: dar um valor padrão para o que falta, avisar ou recusar quando alguém cria um campo. São os dois metamétodos mais usados do Lua: é com o __index que se fazem as classes.

Você vai aprender
  • Quando o Lua consulta o __index: só quando a chave não existe na tabela.
  • O __index como tabela: as configurações padrão da Ana, e a corrente de procura (tabela → manual → outra tabela).
  • O __index como função: um estoque em que todo produto começa com 0.
  • O __newindex como função (para avisar ou validar) e como tabela (para guardar em outro lugar).
  • Como fazer uma tabela só de leitura, com uma mensagem de erro que aponta para a linha certa.
  • Os erros reais: o nil na conta, o return esquecido, o nome errado do metamétodo.

Todos os programas rodaram no Lua 5.5 da máquina da Ana (usuária ana, computador notebook) com lua arquivo.lua. Antes, faça a aula Metatabelas: aqui usamos setmetatable o tempo todo.

A ideia: "se não estiver aqui, pergunte ao gerente"

Na padaria do bairro, o caixa novo tem um caderninho com os preços que ele já decorou. Quando um cliente pergunta o preço de algo que não está no caderninho, ele não responde "não existe": ele pergunta ao gerente. E quando alguém quer anotar um produto novo no caderninho, a regra da loja pode ser "só com autorização do gerente".

  • O caderninho é a tabela.
  • "Se não estiver aqui, pergunte ao gerente" é o __index: o que fazer quando alguém lê uma chave que falta.
  • "Para anotar uma coisa nova, fale com o gerente" é o __newindex: o que fazer quando alguém grava uma chave que ainda não existe.

O que já está no caderninho continua sendo lido e mudado direto, sem incomodar o gerente. Guarde essa regra: ela vale para os dois metamétodos.

1. O problema: a chave que falta

local estoque = { pao = 40, leite = 12 }
print(estoque.pao)
print(estoque.cafe)
estoque.cafe = estoque.cafe + 5

$ lua faltando.lua
40
nil
lua: faltando.lua:4: attempt to perform arithmetic on a nil value (field 'cafe')
stack traceback:
	faltando.lua:4: in main chunk
	[C]: in ?

O estoque.cafe não existe, então vale nil. Mostrar nil não é erro, mas fazer conta com ele é: "tentativa de fazer aritmética com um valor nil (o campo cafe)". O Lua até diz que era um campo (field) de tabela. Veja O Valor nil. Daqui a pouco, o __index vai fazer esse programa funcionar sem mudar a linha 4.

2. __index como tabela: valores padrão

A Ana está escrevendo um editor de textos. Cada pessoa pode escolher a cor, o tamanho da letra e se quer som. Quem não escolher fica com o padrão. Em vez de copiar o padrão para cada pessoa, ela guarda só o que a pessoa mudou e manda o resto "perguntar ao padrão":

local padrao = { cor = "azul", tamanho = 12, som = true }

local config_ana = setmetatable({ cor = "verde" }, { __index = padrao })

print(config_ana.cor)
print(config_ana.tamanho)
print(config_ana.som)
print(config_ana.idioma)

$ lua padrao.lua
verde
12
true
nil
{ __index = padrao }
A metatabela, escrita direto dentro do setmetatable. O campo __index aponta para a tabela padrao: "o que faltar em config_ana, procure em padrao".
config_ana.cor → verde
A chave cor existe em config_ana: o Lua devolve na hora e nem olha a metatabela.
config_ana.tamanho → 12
A chave tamanho não existe em config_ana. O Lua olha a metatabela, acha o __index, e procura tamanho em padrao: 12.
config_ana.idioma → nil
Não está em config_ana nem em padrao: aí, sim, a resposta é nil.

Passo a passo de config_ana.tamanho:

  1. O Lua procura tamanho na própria config_ana. Não acha.
  2. A config_ana tem metatabela? Tem. E a metatabela tem __index? Tem: é a tabela padrao.
  3. O Lua procura tamanho em padrao, e acha 12.

O padrão não é copiado

O __index não copia nada: a config_ana continua só com o que é dela. Por isso, mudar o padrão muda para todo mundo que ainda não escolheu, e gravar na config_ana não estraga o padrão:

local padrao = { cor = "azul", tamanho = 12 }
local config_ana = setmetatable({ cor = "verde" }, { __index = padrao })

padrao.tamanho = 14
print(config_ana.tamanho)

config_ana.tamanho = 20
print(config_ana.tamanho, padrao.tamanho)

for chave, valor in pairs(config_ana) do
  print("própria:", chave, valor)
end

$ lua padrao2.lua
14
20	14
própria:	cor	verde
própria:	tamanho	20

O config_ana.tamanho = 20 criou o campo na própria config_ana (o __index só cuida da leitura). A partir daí, ela tem o seu tamanho e não pergunta mais ao padrão. E o pairs só mostra o que é dela: cor e tamanho, nada do padrão. (A ordem das duas linhas do pairs pode mudar de uma execução para outra; no lab, numa de cinco vezes o tamanho veio primeiro. Veja pairs.)

Missão: a Bia só escolheu a cor, e o programa mostra Tamanho da letra: nil. Use setmetatable com um __index apontando para padrao, para ela herdar o tamanho 12.

local padrao = { cor = "azul", tamanho = 12, som = true }

3. A corrente de procura

E se a tabela do __index também tiver metatabela com __index? O Lua continua procurando, elo por elo, até achar ou até a corrente acabar:

local fabrica = { garantia = "1 ano" }
local modelo = setmetatable({ cor = "preta", voltagem = 127 }, { __index = fabrica })
local cafeteira = setmetatable({ dono = "Ana" }, { __index = modelo })

print(cafeteira.dono)
print(cafeteira.cor)
print(cafeteira.garantia)
print(cafeteira.manual)

$ lua corrente.lua
Ana
preta
1 ano
nil

A cafeteira da Ana tem só o dono. A cor vem do modelo; a garantia, que nem o modelo tem, vem da fábrica. O manual não está em lugar nenhum: nil. Essa corrente é exatamente o que faz a herança funcionar.

4. __index como função: o estoque que começa em zero

O __index também pode ser uma função. Aí, quando falta uma chave, o Lua chama a função com dois valores: a tabela e a chave procurada. O que a função devolver vira a resposta.

local estoque = setmetatable({ pao = 40 }, {
  __index = function (tabela, chave)
    print("  (procurou '" .. chave .. "', que não existe)")
    return 0
  end,
})

print("pão:", estoque.pao)
print("café:", estoque.cafe)
estoque.cafe = estoque.cafe + 5
print("café:", estoque.cafe)

$ lua funcao.lua
pão:	40
  (procurou 'cafe', que não existe)
café:	0
  (procurou 'cafe', que não existe)
café:	5
__index = function (tabela, chave)
A função recebe a tabela onde a chave faltou (aqui, o próprio estoque) e a chave (o texto "cafe").
return 0
A resposta para qualquer chave que falte: zero. É o "valor padrão" do estoque.
estoque.pao → 40, sem aviso
O pao existe: a função nem foi chamada.
(procurou 'cafe'…) duas vezes
Uma para o print, outra para o estoque.cafe + 5. Depois do estoque.cafe = 5, o café passou a existir, e o último print leu direto, sem chamar a função.

O programa da seção 1, que dava erro na linha estoque.cafe = estoque.cafe + 5, agora funciona. A diferença em relação ao __index tabela: a função pode calcular a resposta (devolver 0, montar um texto, buscar em outro lugar), em vez de só procurar numa tabela fixa.

Missão: o programa conta quantas vezes cada produto foi vendido, mas a primeira venda de cada produto dá attempt to perform arithmetic on a nil value. Ligue à tabela vendas uma metatabela com um __index função que devolve 0.

local vendas = {}

local pedidos = { "pao", "cafe", "pao", "bolo", "cafe", "pao" }
for _, produto in ipairs(pedidos) do
  vendas[produto] = vendas[produto] + 1
end

print("pão: " .. vendas.pao)
print("café: " .. vendas.cafe)
print("bolo: " .. vendas.bolo)
print("leite: " .. vendas.leite)

    return 0
  end,
})

local pedidos = { "pao", "cafe", "pao", "bolo", "cafe", "pao" }
for _, produto in ipairs(pedidos) do
  vendas[produto] = vendas[produto] + 1
end

print("pão: " .. vendas.pao)
print("café: " .. vendas.cafe)
print("bolo: " .. vendas.bolo)
print("leite: " .. vendas.leite)

5. __newindex: quando alguém cria uma chave

O __newindex é o par do __index para a gravação. Ele entra em ação quando alguém faz t.chave = valor e a chave ainda não existe em t. Como função, ele recebe três valores: a tabela, a chave e o valor.

local estoque = setmetatable({ pao = 40 }, {
  __newindex = function (tabela, chave, valor)
    print("  (tentou criar '" .. chave .. "' = " .. tostring(valor) .. ")")
  end,
})

estoque.pao = 35
print("pão:", estoque.pao)
estoque.cafe = 10
print("café:", estoque.cafe)

$ lua newindex.lua
pão:	35
  (tentou criar 'cafe' = 10)
café:	nil
estoque.pao = 35
O pao já existia: a gravação foi direta, sem chamar o __newindex.
estoque.cafe = 10
O cafe não existia: em vez de criar, o Lua chamou o __newindex com (estoque, "cafe", 10).
café: nil
Atenção: o valor não foi guardado! Quando existe __newindex, o Lua passa a gravação para ele e não grava nada sozinho. Se a função não guardar o valor em algum lugar, ele se perde.

Para o __newindex função guardar o valor na própria tabela, ele não pode escrever tabela[chave] = valor (isso chamaria o __newindex de novo, para sempre). Ele precisa do rawset, que grava "por baixo" do manual. Isso tem aula própria: rawget, rawset e rawequal. Nesta aula, usamos outro truque: guardar numa outra tabela.

__newindex como tabela

Se o __newindex for uma tabela, as chaves novas são gravadas nela, e não na tabela original:

local novidades = {}
local estoque = setmetatable({ pao = 40 }, { __newindex = novidades })

estoque.pao = 35
estoque.cafe = 10
estoque.bolo = 3
print(estoque.pao, estoque.cafe, estoque.bolo)
print(novidades.cafe, novidades.bolo)

$ lua newindex_tab.lua
35	nil	nil
10	3

O pao (que já existia) foi mudado no próprio estoque. O café e o bolo foram parar em novidades, e por isso estoque.cafe continua nil. Juntando com um __index que aponta para a mesma tabela, dá para ler de volta o que foi guardado lá. É o que a seção seguinte faz.

Validar antes de guardar

A Ana quer que o estoque recuse quantidades negativas ou que não sejam números. A tabela que o programa usa (estoque) fica vazia, e os valores de verdade moram em guardado. Como o estoque nunca ganha chave nenhuma, toda gravação passa pelo __newindex, e toda leitura passa pelo __index:

local guardado = {}
local estoque = setmetatable({}, {
  __index = guardado,
  __newindex = function (tabela, chave, valor)
    if type(valor) ~= "number" or valor < 0 then
      error("quantidade inválida para '" .. chave .. "': " .. tostring(valor), 2)
    end
    guardado[chave] = valor
  end,
})

estoque.pao = 40
estoque.leite = 12
print(estoque.pao, estoque.leite)
estoque.cafe = -3
print("esta linha não aparece")

$ lua validar.lua
40	12
lua: validar.lua:15: quantidade inválida para 'cafe': -3
stack traceback:
	[C]: in global 'error'
	validar.lua:6: in metamethod 'newindex'
	validar.lua:15: in main chunk
	[C]: in ?
guardado[chave] = valor
Quando o valor é bom, ele vai para a tabela guardado (que não tem metatabela, então é uma gravação comum).
error("…", 2)
Quando é ruim, o programa para com uma mensagem nossa (veja error). O 2 é o nível: "culpe quem chamou". Por isso a mensagem diz validar.lua:15:, a linha do estoque.cafe = -3, onde está o engano de verdade, e não a linha 6, onde está o error.
validar.lua:6: in metamethod 'newindex'
O rastro mostra o caminho completo: a linha 15 disparou o metamétodo, e dentro dele a linha 6 chamou o error.

6. A tabela só de leitura

Os dias da semana não mudam. A Ana quer uma tabela que ninguém consiga alterar sem querer. A receita é a mesma da validação: uma tabela vazia na frente (o "balcão"), com __index apontando para os dados de verdade e um __newindex que sempre recusa:

local function somente_leitura(original)
  return setmetatable({}, {
    __index = original,
    __newindex = function (tabela, chave, valor)
      error("tabela só de leitura: não dá para mudar '" .. tostring(chave) .. "'", 2)
    end,
  })
end

local dias = somente_leitura({ "dom", "seg", "ter", "qua", "qui", "sex", "sáb" })
print(dias[1], dias[7])
dias[1] = "domingo"

$ lua leitura.lua
dom	sáb
lua: leitura.lua:12: tabela só de leitura: não dá para mudar '1'
stack traceback:
	[C]: in global 'error'
	leitura.lua:5: in metamethod 'newindex'
	leitura.lua:12: in main chunk
	[C]: in ?

Por que a tabela da frente precisa estar vazia? Porque o __newindex só é chamado para chaves que não existem nela. Se ela tivesse o [1] = "dom", o dias[1] = "domingo" mudaria direto, sem passar pelo manual. Vazia, toda gravação é "nova" e cai no error.

E o nível 2 faz diferença? Sem ele (só error("…")), a mensagem aponta para a linha do próprio error:

$ lua leitura_nivel1.lua
lua: leitura_nivel1.lua:5: tabela só de leitura: não dá para mudar '1'
stack traceback:
	[C]: in global 'error'
	leitura_nivel1.lua:5: in metamethod 'newindex'
	leitura_nivel1.lua:11: in main chunk
	[C]: in ?

Quem lê leitura_nivel1.lua:5 vai procurar o erro dentro da somente_leitura, que está certa. Com o nível 2, a primeira linha já aponta para quem tentou mudar.

O balcão vazio engana o # e o pairs

Como a tabela da frente está vazia, #dias deu 0 no lab, e um pairs(dias) não passou por nenhuma chave. O ipairs funcionou (mostrou 1 dom, 2 seg, 3 ter), porque no Lua 5.5 ele lê dias[1], dias[2]… e respeita o __index. (No lua5.1 e no luajit do lab, o mesmo ipairs não mostrou nada.) O # se conserta com o metamétodo __len, na aula __tostring, __call e __len.

Formas diferentes de fazer a mesma coisa

Valor padrão para o que falta, de três jeitos:

-- 1) sem metatabela: o "or" na hora de ler
local qtd = estoque.cafe or 0

-- 2) __index tabela: os padrões ficam numa tabela
local config = setmetatable({}, { __index = { tamanho = 12, cor = "azul" } })

-- 3) __index função: o padrão é calculado
local vendas = setmetatable({}, { __index = function () return 0 end })
SituaçãoQual usar
O padrão é usado em um ou dois lugares do programat.chave or padrao (veja O Truque do and/or): simples e sem surpresa
Um conjunto de padrões compartilhado (configurações, modelo, "classe")__index tabela
O padrão é igual para qualquer chave (contadores) ou precisa ser calculado__index função
Avisar, validar ou recusar gravaçõesTabela vazia na frente + __index + __newindex função
Mandar as chaves novas para outra tabela__newindex tabela
O or tem uma pegadinha

t.som or true dá true mesmo quando a pessoa gravou som = false, porque false or true é true. O __index não tem esse problema: se som = false estiver na tabela, a chave existe, e o padrão nem é consultado.

Quando dá errado

Esqueceu o return no __index função 
local estoque = setmetatable({}, {
  __index = function (tabela, chave)
    local padrao = 0
  end,
})
print(estoque.cafe)
print(estoque.cafe + 5)

$ lua esqueceu_return2.lua
nil
lua: esqueceu_return2.lua:7: attempt to perform arithmetic on a nil value (field 'cafe')
stack traceback:
	esqueceu_return2.lua:7: in main chunk
	[C]: in ?

A função foi chamada, mas não devolveu nada, e "nada" vira nil. É o mesmo erro da seção 1, como se o __index nem existisse. Como consertar: return 0. E só escrever 0 sozinho numa linha também não serve: o Lua dá erro de sintaxe, unexpected symbol near '0' ("símbolo inesperado perto de 0"), porque um valor solto não é um comando.

Escreveu o nome do metamétodo errado 
local padrao = { tamanho = 12 }
local config = setmetatable({}, { __indx = padrao })
print(config.tamanho)

$ lua indx.lua
nil

Sem erro nenhum, só um nil silencioso. O Lua procura exatamente __index; o __indx é um campo comum, que ele ignora. Erros de digitação no nome do metamétodo são traiçoeiros justamente por isso. Como consertar: __index (dois sublinhados, "index" completo).

Usou a tabela do padrão antes de criá-la 
local config = setmetatable({}, { __index = padrao })
local padrao = { tamanho = 12 }
print(config.tamanho)

$ lua ordem.lua
nil

Na linha 1, a variável padrao ainda não existe (vale nil), então o __index foi gravado como nil, que é o mesmo que não ter __index. A tabela criada na linha 2 chega tarde. Como consertar: crie o padrao antes do setmetatable. (O manual guarda a tabela que a variável tinha naquele momento.)

Gravou pelo __newindex e o valor sumiu

Na seção 5, o estoque.cafe = 10 seguido de print(estoque.cafe) mostrou nil. Não é defeito do Lua: com __newindex, gravar é tarefa sua. Como consertar: dentro da função, guarde o valor em outra tabela (guardado[chave] = valor, com __index = guardado) ou use rawset(tabela, chave, valor) (aula rawget e rawset).

Pôs um valor que não é tabela nem função no __index 
local config = setmetatable({}, { __index = 12 })
print(config.tamanho)

$ lua idx_num.lua
lua: idx_num.lua:2: attempt to index a number value
stack traceback:
	idx_num.lua:2: in main chunk
	[C]: in ?

O Lua tentou procurar tamanho "dentro" do número 12: "tentativa de indexar um valor número". O __index tem de ser uma tabela ou uma função. Como consertar: se a ideia era "todo campo vale 12", use uma função: __index = function () return 12 end.

Resumo

  • __index responde à leitura de uma chave que não existe; __newindex, à gravação de uma chave que não existe. Chaves que já existem são lidas e gravadas direto.
  • __index tabela: "procure lá" (valores padrão, e a corrente de procura das classes e da herança). __index função: (tabela, chave), e o que ela devolve é a resposta.
  • __newindex tabela: grava as chaves novas em outra tabela. __newindex função: (tabela, chave, valor), e nada é gravado se ela não gravar.
  • Tabela vazia na frente + __index + __newindex = controle total: validar, avisar, ou recusar (tabela só de leitura). Use error(msg, 2) para culpar a linha certa.
  • Cuidado com o nome do metamétodo e com o return: os dois erros dão só um nil silencioso.
  • Próximo passo: __tostring, __call e __len.
