Lua Tabelas Fracas

Toda tabela que você criou até aqui segura o que está dentro dela: enquanto um item estiver guardado na tabela, o Lua nunca o apaga da memória. Quase sempre é isso que você quer. Mas às vezes a tabela é só um lembrete ("se eu ainda tiver isto, me lembre") e não deveria impedir que a coisa vá embora. Para isso existem as tabelas fracas (em inglês, weak tables): tabelas que guardam itens sem segurá-los. Você liga isso com um campo da metatabela chamado __mode ("modo").

Você vai aprender
  • O que o coletor de lixo faz e o que é uma referência forte e uma fraca.
  • Como fazer uma tabela de valores fracos (__mode = "v") e ver, com collectgarbage(), um item sumir.
  • Como fazer uma tabela de chaves fracas (__mode = "k") para anotar coisas sobre objetos dos outros.
  • O que nunca sai de uma tabela fraca: números, textos e booleanos.
  • Um cache que se limpa sozinho e os erros mais comuns (inclusive o mais traiçoeiro: o item que "não quer sumir").

Todos os programas desta aula rodaram no Lua 5.5 da máquina da Ana (usuária ana, computador notebook), salvos na pasta pessoal dela e executados com lua arquivo.lua. Para entender esta aula, você precisa saber o que é uma metatabela (aula Metatabelas) e que uma tabela é uma referência (aula Tabelas São Referências).

A ideia: o caderno de fiado e a lista de achados e perdidos

Pense em duas listas penduradas na padaria do bairro:

  • O caderno de fiado: o que está anotado ali, o padeiro não deixa sumir. Enquanto o nome estiver no caderno, a conta continua existindo. Isso é uma referência forte.
  • O quadro de achados e perdidos: "guarda-chuva azul, guardado no balcão". Quando o dono passa e leva o guarda-chuva, a linha do quadro some sozinha: ninguém precisa apagá-la. O quadro só aponta para o guarda-chuva; não o prende na padaria. Isso é uma referência fraca.

No Lua, quem leva embora as coisas que ninguém mais usa é o coletor de lixo (em inglês, garbage collector). De tempos em tempos, ele procura tabelas, funções e outros objetos que nenhuma variável e nenhuma tabela consegue mais alcançar, e libera a memória deles. Ele trabalha sozinho, sem você pedir (a aula Coleta de Lixo mostra os detalhes).

A regra dele é simples: se alguém ainda segura o objeto, ele fica. Uma tabela comum segura tudo o que guarda. Uma tabela fraca guarda sem segurar: para o coletor, o que só está numa tabela fraca é como se não estivesse em lugar nenhum.

1. Primeiro, uma tabela comum: nada some

Para comparar depois, veja o que acontece com uma tabela normal. A Ana guarda as fichas de duas clientes numa tabela cache ("cache" é o nome que os programadores dão a um lugar onde se guardam coisas para usar de novo depois). Depois ela chama collectgarbage(), que manda o coletor de lixo fazer uma faxina completa agora:

local cache = {}
cache.ana = { nome = "Ana" }
cache.bia = { nome = "Bia" }
collectgarbage()
local n = 0
for _ in pairs(cache) do n = n + 1 end
print("itens:", n)

$ lua forte.lua
itens:	2

As duas fichas continuam lá. A própria tabela cache segura as duas, então o coletor não pode levar nenhuma. O laço com pairs só conta os itens (o # não serve aqui, porque as chaves são textos; veja pairs).

2. Valores fracos: __mode = "v"

Agora o mesmo cache, com uma diferença: ele ganha uma metatabela com o campo __mode = "v". O "v" é de value, "valor": os valores desta tabela são fracos. E desta vez a Ana guarda a ficha dela também numa variável, guardada:

local cache = setmetatable({}, { __mode = "v" })
cache.ana = { nome = "Ana" }
cache.bia = { nome = "Bia" }
local guardada = cache.ana
local function conta(t)
  local n = 0
  for _ in pairs(t) do n = n + 1 end
  return n
end
print("antes:", conta(cache))
collectgarbage()
print("depois:", conta(cache))
print(cache.ana, cache.bia)
print(cache.ana == guardada, cache.bia)
setmetatable({}, { __mode = "v" })
Cria uma tabela vazia e dá a ela uma metatabela. O setmetatable devolve a própria tabela, por isso dá para criar e guardar numa linha só. A metatabela tem um único campo, __mode, com o texto "v".
cache.ana = { nome = "Ana" }
Guarda uma tabela nova no cache. Neste momento, quem segura a ficha da Ana? Só o cache, e fracamente.
local guardada = cache.ana
Agora a variável guardada também aponta para a ficha da Ana. Uma variável é uma referência forte: enquanto ela existir, a ficha da Ana não pode ir embora.
local function conta(t)
Uma função pequena que conta quantos pares chave/valor a tabela tem.
collectgarbage()
"Colete o lixo": pede uma coleta completa agora. Num programa normal você não precisa chamar isso; aqui é só para ver o efeito na hora, em vez de esperar o coletor passar sozinho.
$ lua fraca_v.lua
antes:	2
depois:	1
table: 0x55f79b171d20	nil
true	nil

A ficha da Bia sumiu, e sozinha: ninguém escreveu cache.bia = nil. Só o cache apontava para ela, e o cache é fraco, então o coletor a levou e o Lua tirou o par bia da tabela. A ficha da Ana ficou, porque a variável guardada ainda a segura. A última linha confirma: cache.ana é a mesma tabela que está em guardada (true), e cache.bia agora é nil.

O número 0x55f79b171d20 é o endereço da tabela na memória. Ele muda a cada vez que você roda (no editor do guia ele também é diferente); o que importa é o resto.

"Fraco" não quer dizer "apaga já"

Uma tabela fraca não apaga nada por conta própria. Ela só deixa o coletor levar o que ninguém mais segura. Sem o collectgarbage(), a ficha da Bia sumiria mais tarde, quando o coletor passasse sozinho: talvez daqui a um milissegundo, talvez só quando o programa tivesse criado muita coisa nova. Por isso, num programa de verdade, nunca conte que um item ainda está numa tabela fraca: sempre teste se ele veio nil.

Missão: este cache é uma tabela comum, então depois da faxina continuam os 3 itens (depois: 3). Faça os valores do cache serem fracos, para sobrar só a ficha que a variável guardada ainda segura (depois: 1).

local cache = {}
cache.ana = { nome = "Ana" }
cache.bia = { nome = "Bia" }
cache.caio = { nome = "Caio" }
local guardada = cache.ana

  local n = 0
  for _ in pairs(t) do n = n + 1 end
  return n
end
print("antes: " .. conta(cache))
collectgarbage()
print("depois: " .. conta(cache))

cache.ana = { nome = "Ana" }
cache.bia = { nome = "Bia" }
cache.caio = { nome = "Caio" }
local guardada = cache.ana
local function conta(t)

  for _ in pairs(t) do n = n + 1 end
  return n

print("antes: " .. conta(cache))
collectgarbage()
print("depois: " .. conta(cache))

No lab, a solução mostrou antes: 3 e depois: 1. Experimente depois apagar a linha local guardada = cache.ana: aí ninguém segura ficha nenhuma, e o "depois" vira 0.

3. Chaves fracas: __mode = "k"

O "k" é de key, "chave": as chaves da tabela são fracas. Isso serve quando a chave é um objeto (uma tabela) que pertence a outra parte do programa, e você quer anotar alguma coisa sobre ele sem atrapalhar a vida dele.

A lojinha da Ana tem as fichas das clientes. Ela quer contar quantas visitas cada uma fez, mas sem mexer nas fichas (que podem ser de outro módulo). Então ela usa a própria ficha como chave de uma tabela visitas:

local visitas = setmetatable({}, { __mode = "k" })
local ana = { nome = "Ana" }
local bia = { nome = "Bia" }
visitas[ana] = 3
visitas[bia] = 1
local function conta(t)
  local n = 0
  for _ in pairs(t) do n = n + 1 end
  return n
end
print("antes:", conta(visitas))
bia = nil
collectgarbage()
print("depois:", conta(visitas))
print(visitas[ana])

$ lua fraca_k.lua
antes:	2
depois:	1
3

Linha por linha:

  • visitas[ana] = 3: a chave é a tabela da Ana (não o texto "Ana"). Qualquer valor pode ser chave no Lua, inclusive uma tabela.
  • bia = nil: a ficha da Bia deixou de ser usada pelo programa (por exemplo, ela saiu do cadastro). A única coisa que ainda aponta para ela é a chave em visitas, e essa chave é fraca.
  • Depois da faxina, o par da Bia sumiu inteiro (a chave e o número 1). O da Ana ficou, porque a variável ana ainda a segura: visitas[ana] continua 3.

Sem o __mode = "k", a tabela visitas seguraria para sempre todas as fichas que já passaram por ela, mesmo as de clientes que o resto do programa já esqueceu. Num programa que roda o dia inteiro (um jogo, um servidor), esse tipo de tabela que só cresce é uma das causas mais comuns de vazamento de memória.

Quando sai um, sai o par

O manual do Lua diz: se a chave ou o valor for coletado, o par inteiro sai da tabela. Por isso, com "v", a chave bia também sumiu (seção 2), e com "k", o número 1 também sumiu.

Os dois ao mesmo tempo: "kv"

Com __mode = "kv", chaves e valores são fracos: o par sai se qualquer um dos dois não for mais seguro por ninguém. É bem menos usado que os outros dois.

__modeO que fica fracoUso típico
"v"os valorescache: "guarde esta ficha enquanto alguém a estiver usando"
"k"as chavesanotações sobre objetos dos outros: "quantas visitas esta ficha teve"
"kv"chaves e valoresraro: ligações entre objetos que podem sumir dos dois lados

4. O que nunca sai de uma tabela fraca

Só sai de uma tabela fraca o que é objeto: tabelas, funções e corrotinas, coisas que foram criadas (com {}, function…). Números, booleanos e textos se comportam como valores: o número 10 não "pertence" a ninguém, e o texto "texto" é igual a qualquer outro "texto". Eles nunca saem. Veja uma tabela com tudo fraco ("kv") e um pouco de cada coisa:

local t = setmetatable({}, { __mode = "kv" })
t[1] = "texto"
t.x = 10
t.y = true
t.z = {}
t[{}] = "chave tabela"
t.f = function () end
collectgarbage()
local chaves = {}
for k, v in pairs(t) do chaves[#chaves + 1] = tostring(type(k)) .. "=" .. type(v) end
table.sort(chaves)
print(table.concat(chaves, " "))

$ lua strings.lua
number=string string=boolean string=number

Sobraram 3 pares: t[1] = "texto" (chave número, valor texto), t.y = true e t.x = 10. Sumiram os três que tinham uma tabela ou uma função que ninguém mais segurava: t.z = {}, t[{}] e t.f. (O table.sort está lá para a lista sair sempre na mesma ordem: a ordem do pairs não é garantida.)

5. Um cache que se limpa sozinho

O uso mais famoso das chaves fracas é lembrar um resultado já calculado para cada objeto (em inglês, memoization, "memorização"). Calcular a área de um retângulo é rápido, mas imagine que fosse uma conta demorada:

local cache = setmetatable({}, { __mode = "k" })
local function area(retangulo)
  local r = cache[retangulo]
  if r then
    print("  (do cache)")
    return r
  end
  print("  (calculando)")
  r = retangulo.largura * retangulo.altura
  cache[retangulo] = r
  return r
end
local sala = { largura = 4, altura = 5 }
print(area(sala))
print(area(sala))

$ lua memo.lua
  (calculando)
20
  (do cache)
20

Na primeira chamada, o resultado não estava no cache: a função calculou e guardou. Na segunda, achou pronto. E como a chave é fraca, quando o programa parar de usar a sala, o resultado guardado vai embora junto, sem ninguém precisar limpar o cache.

Experimente: crie um segundo retângulo (local quarto = { largura = 3, altura = 3 }) e chame area(quarto) duas vezes. Depois troque o __mode = "k" por "v" e pense: os valores aqui são números. Eles sairiam do cache algum dia?

local cache = setmetatable({}, { __mode = "k" })
local function area(retangulo)
  local r = cache[retangulo]
  if r then
    print("  (do cache)")
    return r
  end
  print("  (calculando)")
  r = retangulo.largura * retangulo.altura
  cache[retangulo] = r
  return r
end
local sala = { largura = 4, altura = 5 }
print(area(sala))
print(area(sala))

(Resposta: com "v", não. Números nunca saem de uma tabela fraca, e as chaves passariam a ser fortes: o cache seguraria todos os retângulos para sempre. Para este cache, o certo é "k".)

6. Chave fraca que aparece no próprio valor

E se o valor guardado apontar de volta para a chave? Por exemplo, a ficha do dono de cada carro guarda o próprio carro:

local dono = setmetatable({}, { __mode = "k" })
local carro = { placa = "ABC1D23" }
dono[carro] = { carro = carro, nome = "Ana" }
carro = nil
collectgarbage()
print(next(dono))

$ lua efemero.lua
nil

O valor { carro = carro, … } segura o carro com força, então parece que o carro nunca poderia sumir. Mas o Lua é esperto: numa tabela de chaves fracas, um valor só conta como "vivo" se a chave dele estiver viva por outro caminho. Como só o próprio valor apontava para o carro, o par inteiro saiu (next(dono) deu nil: a tabela ficou vazia). O manual chama esse tipo de tabela de tabela efêmera (ephemeron table).

Formas diferentes de fazer a mesma coisa

A metatabela pode ser criada na hora, como em todos os exemplos, ou ficar guardada numa variável e ser usada por várias tabelas:

-- 1) metatabela criada na hora
local cache1 = setmetatable({}, { __mode = "v" })

-- 2) uma metatabela só, para várias tabelas fracas
local fraca_v = { __mode = "v" }
local cache2 = setmetatable({}, fraca_v)
local cache3 = setmetatable({}, fraca_v)

-- 3) a tabela primeiro, a metatabela depois
local cache4 = {}
setmetatable(cache4, { __mode = "v" })

E, claro, a outra forma de fazer um item sumir é a de sempre: apagá-lo você mesmo com cache.bia = nil.

SituaçãoQual usar
Você sabe exatamente quando o item deixa de servirUma tabela comum e t[chave] = nil na hora certa: é mais claro e previsível
Guardar objetos para reaproveitar enquanto alguém ainda os usa__mode = "v"
Anotar dados sobre objetos que não são seus (contadores, resultados calculados)__mode = "k"
Os valores são números, textos ou booleanos"v" não adianta: eles nunca saem

Quando dá errado

Pôs o __mode na própria tabela, sem metatabela 
local cache = { __mode = "v" }
cache.ana = { nome = "Ana" }
collectgarbage()
print(cache.ana)

$ lua esqueceu.lua
table: 0x55f8db55d4e0

Nenhum erro, e nada some. Aqui __mode é só um campo comum da tabela cache, como seria cor ou nome. O Lua só olha o __mode que está na metatabela. Como consertar: local cache = setmetatable({}, { __mode = "v" }).

O item "não quer sumir" 
local cache = setmetatable({}, { __mode = "v" })
local ana = { nome = "Ana" }
cache.ana = ana
collectgarbage()
print(cache.ana.nome)

$ lua ainda.lua
Ana

A tabela é fraca, mas a ficha continua lá. Não é defeito: a variável local ana ainda segura a ficha com força. Enquanto houver qualquer referência forte (uma variável, outra tabela comum, uma closure que use o objeto), o coletor não leva nada. Quando um item não some, procure quem ainda está segurando ele.

Usou o item sem conferir se ele ainda existe 
local cache = setmetatable({}, { __mode = "v" })
cache.bia = { nome = "Bia" }
collectgarbage()
print(cache.bia.nome)

Como consertar: numa tabela fraca, todo item pode virar nil a qualquer momento. Teste antes: local ficha = cache.bia; if ficha then print(ficha.nome) end.

Escreveu o modo errado 
$ lua -e 'local t = setmetatable({}, {__mode="x"}) t[{}]=1 collectgarbage() print(next(t))'
table: 0x564354d1e970	1

O Lua não reclama de um __mode estranho ("x", "V", "chave"): ele simplesmente não vê nem k nem v, e a tabela continua forte. O item que ninguém segura não saiu. Os únicos valores que o manual aceita são "k", "v" e "kv", em minúsculas.

Tentou dar metatabela a um texto 
$ lua -e 'setmetatable("abc", { __mode = "k" })'
lua: (command line):1: bad argument #1 to 'setmetatable' (table expected, got string)
stack traceback:
	[C]: in global 'setmetatable'
	(command line):1: in main chunk
	[C]: in ?

"Argumento ruim nº 1 para o setmetatable (era esperada uma tabela, veio um texto)". Só tabelas podem ser fracas, e o setmetatable do Lua só aceita tabelas. O [C]: in global 'setmetatable' do rastro diz que o erro foi descoberto dentro da função setmetatable, que é escrita em C.

E nas outras versões?

Tabelas fracas existem há muito tempo: o fraca_k.lua desta aula deu o mesmo resultado no Lua 5.4, no 5.1 e no LuaJIT do lab (antes: 2, depois: 1, 3). O que mudou ao longo das versões foram detalhes do coletor (veja as diferenças entre as versões).

Resumo

  • O coletor de lixo leva os objetos que ninguém mais segura. Uma tabela comum segura tudo o que guarda; uma tabela fraca guarda sem segurar.
  • A fraqueza vem do campo __mode da metatabela: "v" (valores fracos), "k" (chaves fracas) ou "kv".
  • Quando a chave ou o valor é coletado, o par inteiro sai da tabela, sem ninguém escrever = nil.
  • Só saem objetos (tabelas, funções, corrotinas). Números, textos e booleanos nunca saem.
  • Use "v" para caches de objetos e "k" para anotar dados sobre objetos dos outros. Sempre teste se o item ainda existe antes de usá-lo.
  • collectgarbage() força uma coleta agora: ótimo para ver o efeito numa aula ou num teste; num programa normal, deixe o coletor trabalhar sozinho.
