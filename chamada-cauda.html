Lua Chamada de Cauda (return f())

Na aula Recursão, você viu que cada chamada que ainda não terminou ocupa um lugar na pilha de chamadas, e que, com umas 500 mil chamadas empilhadas, o Lua para com stack overflow. Existe uma exceção a essa regra, e o Lua é uma das poucas linguagens populares que a garante: quando a última coisa que uma função faz é return outra_funcao(...), a chamada nova ocupa o lugar da antiga em vez de empilhar. Isso se chama chamada de cauda (em inglês, tail call: a chamada que fica "no rabo" da função).

Você vai aprender
  • O que é uma chamada de cauda e por que ela não ocupa pilha.
  • Uma contagem de um milhão de chamadas recursivas que funciona, e a quase igual que estoura.
  • A técnica do acumulador, que transforma uma recursão comum em chamada de cauda.
  • Exatamente quais formas de return contam como chamada de cauda (e as que parecem, mas não contam), testadas uma a uma no lab.
  • A linha (...tail calls...) do stack traceback e o que ela esconde.
  • Um passeio pela casa da Ana feito de funções que passam a vez umas para as outras.

Todos os programas desta aula rodaram no Lua 5.5 da máquina da Ana (usuária ana, computador notebook) com lua arquivo.lua.

A ideia: passar o bastão em vez de esperar

Pense no atendimento de uma loja por telefone. Você liga, a atendente não sabe responder, e há dois jeitos de ela agir:

  • "Aguarde na linha." Ela liga para o setor de vendas e fica com você na espera. O setor de vendas também não sabe, liga para o estoque e fica na espera… Cada pessoa ocupa uma linha telefônica, esperando a resposta voltar. Com gente demais esperando, as linhas acabam. Essa é a recursão comum: cada chamada fica parada esperando, ocupando a pilha.
  • "Vou transferir a sua ligação." Ela passa você direto para o setor de vendas e desliga. Ela não precisa saber a resposta, porque não vai fazer mais nada com ela. Vendas transfere para o estoque e desliga também. Só uma linha fica ocupada, por mais transferências que haja. Essa é a chamada de cauda.

A atendente só pode transferir e desligar se não tiver mais nada a fazer depois. Se ela precisasse anotar a resposta, somar alguma coisa ou dar um recado, teria de esperar na linha. É exatamente essa a regra do Lua: a chamada só é de cauda se for a última coisa que a função faz, e se o resultado dela for devolvido sem nenhuma mudança.

2. O que é e o que não é chamada de cauda

A regra oficial do manual do Lua é curta: uma chamada de cauda tem a forma return função(argumentos), e nada mais. Qualquer coisa que a função precise fazer com o resultado depois da chamada estraga a cauda. Para não depender de teoria, cada linha da tabela abaixo foi testada no lab com o mesmo programa, trocando só a linha da chamada recursiva:

local function f(n)
  if n == 0 then return "fim" end
  return f(n - 1)
end
print(pcall(f, 1000000))

$ lua c_a.lua
true	fim

(O pcall roda a função "protegida": devolve true e o resultado se deu certo, ou false e a mensagem de erro, sem quebrar o programa.) Com as outras formas no lugar da linha 3:

Um último caso, mais raro: dentro do escopo de uma variável <close> (veja Fechamento Automático), o return f(n - 1) também deixa de ser de cauda, porque a função ainda precisa "fechar" a variável depois. No lab, com local x <close> = nil antes da linha 3, deu false c_k.lua:4: stack overflow. O manual do Lua 5.5 diz isso com todas as letras: é chamada de cauda o return de uma chamada "fora do escopo de uma variável a ser fechada".

Os parênteses são a pegadinha mais traiçoeira: return (f(n - 1)) parece idêntico a return f(n - 1), mas não é de cauda. E a conta mais comum de todas, return n * fatorial(n - 1), também não é: a multiplicação acontece depois que a chamada volta.

3. O acumulador: levando a conta junto

Como fazer o fatorial, ou a soma de 1 até n, com chamada de cauda, se a conta acontece depois da chamada? O truque é levar a conta junto: em vez de cada chamada esperar a resposta para somar, ela soma antes e passa o resultado parcial para a próxima, num parâmetro a mais. Esse parâmetro se chama acumulador.

A soma comum (a da aula de recursão) estoura com um milhão:

local function soma_ate(n)
  if n == 0 then
    return 0
  end
  return n + soma_ate(n - 1)
end

print(soma_ate(100))
print(soma_ate(1000000))

$ lua soma_normal.lua
5050
lua: soma_normal.lua:5: stack overflow
stack traceback:
	soma_normal.lua:5: in upvalue 'soma_ate'
	…                                « e o resto do rastro, como na seção 1

A versão com acumulador:

local function soma_ate(n, acumulado)
  acumulado = acumulado or 0
  if n == 0 then
    return acumulado
  end
  return soma_ate(n - 1, acumulado + n)
end

print(soma_ate(4))
print(soma_ate(100))
print(soma_ate(1000000))

$ lua soma_acc.lua
10
5050
500000500000
soma_ate(n, acumulado)
Um parâmetro a mais: quanto já foi somado até agora.
acumulado = acumulado or 0
Quem chama de fora escreve só soma_ate(4); aí o acumulado chega nil e começa em 0.
if n == 0 then return acumulado end
O caso base devolve a conta pronta: ela foi sendo feita no caminho.
return soma_ate(n - 1, acumulado + n)
A soma acontece antes da chamada (dentro dos argumentos). Depois dela, não sobra nada a fazer: é uma chamada de cauda.

Veja a diferença na conta de soma_ate(4):

= 4 + (3 + (2 + soma_ate(1)))
= 4 + (3 + (2 + (1 + 0)))

→ soma_ate(3, 4)
→ soma_ate(2, 7)
→ soma_ate(1, 9)
→ soma_ate(0, 10) → 10

Na coluna da esquerda, a expressão vai crescendo: cada parêntese aberto é uma chamada esperando na pilha. Na da direita, a linha nunca cresce: cada chamada só passa o bastão.

4. O que o stack traceback mostra numa chamada de cauda

Se a chamada de cauda joga fora a função anterior, o que sobra para o rastro do erro mostrar? Veja o caixa da padaria, em que três funções passam a vez com return, e a última tem um erro:

local function pagar(valor)
  return valor + nil
end

local function fechar_conta(itens)
  local total = 0
  for _, p in ipairs(itens) do total = total + p end
  return pagar(total)
end

local function caixa()
  return fechar_conta({4, 6})
end

caixa()

$ lua rastro_cauda.lua
lua: rastro_cauda.lua:2: attempt to perform arithmetic on a nil value
stack traceback:
	rastro_cauda.lua:2: in function <rastro_cauda.lua:1>
	(...tail calls...)
	rastro_cauda.lua:15: in main chunk
	[C]: in ?
rastro_cauda.lua:2: in function <rastro_cauda.lua:1>
O erro foi na linha 2, numa função definida na linha 1. Repare que o nome pagar sumiu: o Lua descobre o nome de uma função olhando quem a chamou, e quem a chamou (a fechar_conta) já foi descartado. Ele só consegue dizer onde ela foi escrita.
(...tail calls...)
"(…chamadas de cauda…)": aqui havia uma ou mais funções que passaram a vez com return, e que não existem mais na pilha. Quantas e quais, o Lua não sabe dizer.
rastro_cauda.lua:15: in main chunk
A linha 15 do programa principal, o caixa(), que começou tudo.

O mesmo programa, com cada return f() trocado por "guarda numa local e depois devolve" (o rastro_normal.lua), mostra o caminho inteiro, com os nomes:

$ lua rastro_normal.lua

stack traceback:
	rastro_normal.lua:2: in upvalue 'pagar'
	rastro_normal.lua:8: in upvalue 'fechar_conta'
	rastro_normal.lua:13: in local 'caixa'
	rastro_normal.lua:17: in main chunk

É o preço da chamada de cauda: menos memória, rastro mais curto. Na maioria das vezes, o in function <arquivo:linha> basta para achar o problema: vá à linha indicada. Se um dia você precisar do caminho completo para investigar um erro, troque temporariamente o return f() por local r = f() return r. (Cada linha do rastro está explicada em Lendo uma Mensagem de Erro.)

E nas outras versões?

A chamada de cauda não é novidade: o Lua 5.1, o LuaJIT e o 5.4 do lab também rodaram o c_a.lua de um milhão sem estourar (true fim). O rastro é que muda. No lua5.1, cada chamada descartada vira uma linha (tail call): ?:

lua5.1: rastro_cauda.lua:2: attempt to perform arithmetic on a nil value
stack traceback:
	rastro_cauda.lua:2: in function <rastro_cauda.lua:1>
	(tail call): ?
	(tail call): ?
	rastro_cauda.lua:15: in main chunk
	[C]: ?

E o LuaJIT, no lab, chamou a função do erro de in function 'caixa', um nome que não é o dela. Moral: numa chamada de cauda, desconfie do nome e confie na linha. Mais em as diferenças entre versões.

5. Funções que passam a vez: um passeio pela casa

A chamada de cauda não serve só para recursão. Ela permite escrever um programa como um conjunto de "lugares", em que cada função faz a sua parte e passa a vez para a próxima, sem nunca voltar. Um joguinho de andar pela casa da Ana:

local sala, cozinha, quintal

function sala()
  print("Você está na SALA. Para onde? (cozinha/quintal/sair)")
  local escolha = io.read()
  if escolha == "cozinha" then return cozinha()
  elseif escolha == "quintal" then return quintal()
  elseif escolha == "sair" or escolha == nil then return "Até logo!"
  else
    print("Não entendi.")
    return sala()
  end
end

function cozinha()
  print("Você está na COZINHA. Tem bolo de fubá! (sala)")
  io.read()
  return sala()
end

function quintal()
  print("Você está no QUINTAL. O cachorro late. (sala)")
  io.read()
  return sala()
end

print(sala())

No terminal da Ana, digitando cozinha, sala, banheiro, quintal, sala e sair:

Declara as três locais antes, porque uma função chama a outra (o mesmo truque da recursão mútua em Recursão). Os function sala() de baixo, sem local, preenchem essas locais.
return cozinha()
"Transfere" para a cozinha. A sala não precisa voltar; ela só passa a vez.
return "Até logo!"
O fim do passeio. Esse texto volta direto para o print da última linha, porque todas as funções do caminho foram descartadas.
escolha == nil
Se a entrada acabar (io.read() devolve nil), o passeio termina em vez de perguntar para sempre.

Por mais voltas que o visitante dê pela casa, a pilha nunca cresce: cada cômodo é uma chamada de cauda. Com cozinha() sem o return, cada visita deixaria uma chamada esperando, e um visitante muito animado acabaria num stack overflow.

Experimente: rode e passeie pela casa digitando os cômodos no terminal da caixa (cozinha, sala, quintal…); para terminar, digite sair. Depois acrescente um cômodo novo, o quarto: uma função quarto() que termina com return sala() (não esqueça de pôr o nome quarto na linha 1) e uma opção a mais no if da sala.

local sala, cozinha, quintal

Formas diferentes de fazer a mesma coisa

A soma de 1 até um milhão, de três jeitos que funcionam:

FormaCódigoQuando usar
Laçolocal s = 0 for i = 1, n do s = s + i endO mais simples e o mais rápido para contas em linha reta. É o jeito normal no Lua.
Recursão com acumulador (cauda)return soma_ate(n - 1, acumulado + n)Quando o problema é naturalmente recursivo e pode ter muitos passos. Também em funções que passam a vez (o passeio pela casa, menus, "máquinas de estados").
Recursão comumreturn n + soma_ate(n - 1)Quando a profundidade é pequena (até alguns milhares), como em árvores e cardápios. Mais fácil de ler, mas estoura perto de 500 mil no Lua 5.5.

Quando dá errado

Achou que era de cauda, mas não era: stack overflow

Os casos da tabela da seção 2: return (f(x)), return f(x) .. "", return n * f(x), local r = f(x) return r. Todos dão stack overflow com muitas chamadas. A pergunta para se fazer é: "depois que a chamada volta, esta função ainda faz alguma coisa?" Se a resposta for sim, não é de cauda. Como consertar: leve a conta junto, num acumulador (seção 3), e deixe o return f(…) limpo.

Chamada de cauda sem caso base: o programa não para nunca 
local function rodar(n)
  return rodar(n + 1)
end
rodar(1)

Numa recursão comum, faltar o caso base dá stack overflow em menos de um segundo. Numa chamada de cauda, a pilha nunca enche, então não há estouro: o programa fica rodando para sempre, como um laço infinito. No terminal, a Ana precisou apertar Ctrl+C:

interrupted! quer dizer "interrompido": foi você que mandou parar. O rastro de novo mostra (...tail calls...) no lugar das chamadas descartadas. No editor do guia, depois de 10 segundos, a caixa para o programa sozinha com a mensagem o editor parou o programa: ele rodou mais de 10 segundos sem terminar — laço infinito?. Como consertar: o mesmo de sempre: um caso base que seja alcançado.

O rastro não mostra quem chamou

Não é um erro do Lua, mas confunde: o erro aparece in function <arquivo.lua:1>, sem nome, e logo abaixo (...tail calls...). É a seção 4. Vá direto à linha da mensagem (arquivo.lua:2:) e, se precisar saber o caminho, troque os return f() do caminho por local r = f() return r enquanto investiga.

Missão final: a soma de um milhão

Missão: esta soma estoura a pilha com um milhão. Reescreva a soma_ate com um acumulador (um segundo parâmetro), para que a chamada recursiva seja de cauda e o programa mostre 5050 e 500000500000. Dica: acumulado = acumulado or 0 deixa a chamada de fora continuar com um argumento só.

local function soma_ate(n)

    return 0
  end
  return n + soma_ate(n - 1)
end

print(soma_ate(100))
print(soma_ate(1000000))

local function soma_ate(n, acumulado)
  acumulado = acumulado or 0
  if n == 0 then
    return acumulado
  end
  return soma_ate(n - 1, acumulado + n)
end

print(soma_ate(100))
print(soma_ate(1000000))

Resumo

  • Uma chamada de cauda é return f(…) como última ação, devolvendo o resultado sem mexer. O Lua a executa no lugar da função atual, sem empilhar.
  • Com ela, uma recursão de um milhão de passos funciona; a mesma recursão sem a cauda estoura com stack overflow perto de 500 mil.
  • Não são de cauda: return (f(x)), return n * f(x), return f(x) .. "", return a, f(x), f(x) sem return, e guardar numa local antes de devolver.
  • Para transformar uma recursão comum, use um acumulador: faça a conta antes da chamada e passe o resultado parcial adiante.
  • No rastro de erro, as funções descartadas viram (...tail calls...), e a função do erro aparece como in function <arquivo:linha>.
  • Chamada de cauda sem caso base não estoura: vira um programa que nunca termina.
