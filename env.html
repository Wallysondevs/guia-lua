Lua _G e _ENV

Você já sabe que uma variável sem local é global. Mas onde ela fica guardada? A resposta é uma das ideias mais bonitas do Lua: as globais moram numa tabela comum, igual às que você cria com {}. Essa tabela tem dois nomes: _G (de global) e _ENV (de environment, "ambiente"). Entendendo os dois, você consegue montar nomes de globais na hora, rodar código de outra pessoa numa caixa fechada, onde ele não alcança os seus arquivos, e caçar globais criadas por engano.

Você vai aprender
  • Que toda global é um campo da tabela _G, e como usar _G["nome"] quando o nome é montado na hora.
  • O que o Lua faz, por baixo, com um nome solto como x: ele vira _ENV.x.
  • Como trocar o ambiente de um trecho com local _ENV.
  • Como rodar código numa "caixa de areia" (sandbox) com load(código, nome, "t", ambiente).
  • Como fazer o Lua reclamar de toda global nova, com uma metatabela em _G.
  • As diferenças com o Lua 5.1 e o LuaJIT, que não têm _ENV.

Todos os programas desta aula rodaram no Lua 5.5 da máquina da Ana (usuária ana, computador notebook), na pasta pessoal dela, com lua arquivo.lua. Antes, veja local, Tabelas como Dicionários e, se puder, A Declaração global.

A ideia: o quadro de avisos da casa

Na casa da Ana, cada pessoa tem as suas anotações no próprio caderno: são as variáveis locais, que só quem tem o caderno vê. E na cozinha há um quadro de avisos que todo mundo lê e onde todo mundo escreve: "conta de luz: dia 10", "senha do wi-fi: …". Esse quadro são as globais.

O quadro é um objeto de verdade, que dá para pegar na mão. Você pode tirar uma foto dele, pendurar um quadro diferente para as visitas (sem a senha do wi-fi), ou colocar um aviso: "quem escrever aqui, me avise". No Lua, o quadro é uma tabela, e você pode fazer exatamente essas coisas com ela.

1. _G: a tabela das globais

nome = "Ana"
print(_G.nome)
_G.cidade = "Recife"
print(cidade)
print(_G.print == print)
print(_G._G == _G)
print(type(_G))

$ lua e1.lua
Ana
Recife
true
true
table

Linha por linha:

nome = "Ana" e _G.nome
Criar a global nome é o mesmo que criar o campo nome da tabela _G. São dois jeitos de escrever a mesma coisa.
_G.cidade = "Recife" e cidade
O caminho contrário: escrever no campo de _G cria a global.
_G.print == print
As funções que vêm com o Lua também são globais, guardadas nessa tabela. O print é o campo print de _G.
_G._G == _G
A tabela guarda a si mesma num campo chamado _G. É por isso que o nome _G funciona: ele próprio é uma global.

O que tem dentro do _G

Como é uma tabela, dá para percorrê-la com pairs. Este programa lista o nome de cada global que existe quando um programa começa (em ordem alfabética, para a saída não mudar de uma vez para a outra):

local nomes = {}
for k in pairs(_G) do nomes[#nomes + 1] = k end
table.sort(nomes)
print(#nomes)
print(table.concat(nomes, " "))

$ lua e2.lua
36
_G _VERSION arg assert collectgarbage coroutine debug dofile error getmetatable io ipairs load loadfile math next os package pairs pcall print rawequal rawget rawlen rawset require select setmetatable string table tonumber tostring type utf8 warn xpcall

São 36 nomes: as funções soltas (print, type, pairs…), as bibliotecas (string, math, io, os…, cada uma é uma tabela com funções dentro), o _VERSION, o arg da linha de comando e o próprio _G. A lista de cada uma está em Funções Globais.

Repare que as variáveis locais não aparecem: elas não moram no _G. Com local x = 1, o print(_G.x) mostrou nil no lab.

Para que serve: nomes montados na hora

Com _G, o nome da global pode ser um texto que o programa monta enquanto roda:

for i = 1, 3 do
  _G["caixa_" .. i] = i * 10
end
print(caixa_1, caixa_2, caixa_3)
local qual = "caixa_2"
print(_G[qual])

$ lua e3.lua
10	20	30
20

É o mesmo t["chave"] dos dicionários (aula Tabelas como Dicionários), usado na tabela das globais.

Missão: o programa quer mostrar o preço do item escolhido, mas a última linha procura uma global chamada preco_item, que não existe (rode para ver o erro attempt to concatenate a nil value). Troque o preco_item por um acesso ao _G que monte o nome "preco_" .. item.

preco_pao = 0.75
preco_cafe = 4.5
preco_leite = 6.2
local item = "cafe"
print("preço do " .. item .. ": " .. preco_item)

preco_pao = 0.75
preco_cafe = 4.5
preco_leite = 6.2
local item = "cafe"
print("preço do " .. item .. ": " .. _G["preco_" .. item])
Na vida real, prefira uma tabela sua

Funciona, mas um programa de verdade guardaria os preços numa tabela própria: local precos = { pao = 0.75, cafe = 4.5 } e precos[item]. É mais seguro (ninguém confunde preço com print) e não enche o quadro de avisos de todo mundo. O _G[nome] é útil quando o nome vem de fora: de um arquivo de configuração, de um comando digitado, de um plugin.

2. _ENV: o que o Lua faz com um nome solto

Agora o segredo. Quando o Lua lê o seu arquivo e encontra um nome que não é local, como x, ele reescreve esse nome como _ENV.x. O manual diz isso com todas as letras: toda referência a uma global var é traduzida para _ENV.var. E todo arquivo começa com uma variável local escondida, chamada _ENV, que aponta para a tabela das globais.

print(_ENV == _G)
x = 10
print(_ENV.x)

$ lua e5.lua
true
10

Normalmente, _ENV e _G são a mesma tabela. Então qual é a diferença?

  • _ENV é a variável que o Lua usa de verdade para achar as globais. Trocou o _ENV, mudou o significado de todo nome solto daquele trecho.
  • _G é só um campo da tabela das globais, que aponta para ela mesma. É um atalho para você chegar à tabela. Apagar o _G não muda nada no funcionamento: com _G = nil na primeira linha, o lab ainda mostrou ainda funciona e o x = 1 / print(x) seguinte deu 1.

Trocando o ambiente com local _ENV

Como _ENV é um nome comum, você pode criar uma variável local com esse nome. A partir dali, os nomes soltos passam a morar na sua tabela:

local print = print
local _ENV = { }
x = 10
print(x)
print(_G)

$ lua e6.lua
10
nil
local print = print
Guarda o print numa variável local antes da troca. Locais não dependem do _ENV, então ele continua funcionando depois.
local _ENV = { }
Daqui para baixo, o "quadro de avisos" é esta tabela vazia.
x = 10
Virou _ENV.x = 10: o x foi parar na tabela nova, e não na tabela das globais de verdade.
print(_G)
O _G também é um nome solto: virou _ENV._G, e a tabela nova não tem esse campo. Resultado: nil.

Sem o local print = print, nem o print existiria mais:

local _ENV = {}
print("oi")

$ lua e7.lua
lua: e7.lua:2: attempt to call a nil value (global 'print')
stack traceback:
	e7.lua:2: in main chunk
	[C]: in ?

"Tentativa de chamar um valor nil (a global 'print')". O Lua procurou print no _ENV atual, a tabela vazia, e achou nil.

O _ENV também pode ser um parâmetro. Aí a função lê os nomes soltos da tabela que receber:

local function com_ambiente(_ENV)
  return a + b
end
print(com_ambiente({ a = 2, b = 3 }))

$ lua e14.lua
5

3. A caixa de areia: load com um ambiente

A função load transforma um texto com código Lua numa função que você pode chamar (a aula load, loadfile e dofile mostra o load em detalhes). O quarto argumento dela é o mais interessante aqui: a tabela que vai servir de _ENV para aquele código. É como dar às visitas um quadro de avisos só delas:

local ambiente = { print = print, nome = "Bia" }
local programa = "print('Olá, ' .. nome); total = 3 * 7"
local f = load(programa, "receita", "t", ambiente)
f()
print(ambiente.total, total)

$ lua e8.lua
Olá, Bia
21	nil
programa
Um texto com código. Poderia ter vindo de um arquivo, de um formulário, de um plugin.
load(programa, "receita", "t", ambiente)
Os quatro argumentos: o código; o nome do pedaço, que aparece nas mensagens de erro; o modo "t" (só texto: nada de código já compilado); e o ambiente.
nome
Dentro do código carregado, nome veio do ambiente: "Bia".
total = 3 * 7
A "global" que o código criou foi parar no ambiente (ambiente.total é 21). As globais de verdade do seu programa não foram tocadas: total continuou nil.

O melhor vem agora: o código carregado só enxerga o que você pôs no ambiente. Ele não tem os, nem io, nem nada que você não deu:

local ambiente = { print = print }
local f = load("os.remove('lista.txt')", "receita", "t", ambiente)
print(pcall(f))

$ lua e9.lua
false	[string "receita"]:1: attempt to index a nil value (global 'os')

O código tentou apagar um arquivo da Ana, e não conseguiu: os não existe no ambiente dele. O pcall (aula pcall) segurou o erro, e o programa da Ana continuou. Repare no nome do pedaço na mensagem: [string "receita"]:1:, "o texto chamado receita, linha 1".

Uma calculadora de fórmulas, protegida

Juntando tudo: uma função que roda o código que a pessoa digitou, só com print, string e math, e que avisa os erros sem derrubar o programa:

local function rodar(codigo)
  local caixa = { print = print, string = string, math = math }
  local f, erro = load(codigo, "=usuario", "t", caixa)
  if not f then return print("erro de sintaxe: " .. erro) end
  local ok, msg = pcall(f)
  if not ok then print("erro: " .. msg) end
end
rodar("print(math.max(3, 9))")
rodar("print(io.open('x'))")
rodar("print(")

$ lua e13.lua
9
erro: usuario:1: attempt to index a nil value (global 'io')
erro de sintaxe: usuario:1: unexpected symbol near <eof>

Três casos: o código bom rodou; o que tentou usar io foi barrado; e o que tinha erro de sintaxe nem virou função (o load devolveu nil e a mensagem, em vez de dar erro). O = no começo do nome ("=usuario") faz a mensagem mostrar usuario:1: em vez de [string "usuario"]:1:.

Uma caixa de areia tem furos que esta aula não fecha

Tirar o os e o io já impede o código de mexer nos seus arquivos. Mas um código malicioso ainda pode, por exemplo, rodar um while true do end e travar o seu programa, ou gastar memória até acabar. E não ponha no ambiente funções como load, require, debug, setmetatable ou rawset sem pensar: elas abrem portas para fora da caixa. Para código de quem você não conhece, uma caixa de areia de verdade dá bem mais trabalho.

Por que o modo "t"

O load aceita também código já compilado (binário, feito com string.dump ou luac). O manual avisa que o Lua não confere esse tipo de código, e que um binário malfeito de propósito pode derrubar o interpretador. O modo "t" recusa binários:

local bin = string.dump(function () return 1 end)
print(load(bin, "binario", "t", {}))

$ lua e11.lua
nil	attempt to load a binary chunk (mode is 't')

"Tentativa de carregar um pedaço binário (o modo é 't')". Para código que vem de fora, use sempre "t".

4. Pegando globais criadas por engano

Como _G é uma tabela, ela pode ter uma metatabela (aula __index e __newindex). Com um __newindex, o Lua avisa toda vez que alguém tentar criar uma global nova; com um __index, toda vez que alguém ler uma global que não existe:

setmetatable(_G, {
  __newindex = function (t, nome, valor)
    error("global nova: " .. nome, 2)
  end,
  __index = function (t, nome)
    error("global que não existe: " .. nome, 2)
  end,
})
local total = 0
local precos = { 4.50, 12.90 }
for i = 1, #precos do
  totl = total + precos[i]
end

$ lua e12.lua
lua: e12.lua:12: global nova: totl
stack traceback:
	[C]: in global 'error'
	e12.lua:3: in metamethod 'newindex'
	e12.lua:12: in main chunk
	[C]: in ?

O erro de digitação da linha 12 (totl no lugar de total) foi pego. O 2 no error(…, 2) faz a mensagem apontar para a linha de quem criou a global (12), e não para a linha do próprio error (veja error). O rastro mostra o caminho: a linha 12 acionou o __newindex (in metamethod 'newindex'), que chamou o error.

Este truque × a declaração global

Esse "modo estrito" é um truque antigo, que funciona em todas as versões do Lua. Ele só avisa ao rodar, e só se a linha errada rodar. No Lua 5.5, a declaração global (aula A Declaração global) pega o mesmo erro antes de rodar, em qualquer linha. Para programas só do 5.5, prefira o global.

Formas diferentes de fazer a mesma coisa

Ler a global nome, de quatro jeitos:

nome = "Ana"
print(nome)          -- 1) o jeito normal (vira _ENV.nome)
print(_G.nome)       -- 2) pelo campo _G
print(_G["nome"])    -- 3) com o nome num texto
print(_ENV.nome)     -- 4) pelo _ENV, como o Lua faz por baixo
SituaçãoQual usar
Usar uma global no dia a diaO nome direto: nome
O nome da global é montado na hora, ou vem de fora_G[texto]
Rodar um texto com código sem deixar ele mexer no seu programaload(codigo, "nome", "t", ambiente) e pcall
Uma função que lê os nomes soltos de uma tabela que você escolheUm parâmetro chamado _ENV (raro: confunde quem lê)
Pegar globais criadas por enganoNo 5.5, a declaração global; em qualquer versão, setmetatable(_G, …)
E nas outras versões?

O _G existe em todas. O _ENV e o quarto argumento do load surgiram no Lua 5.2, que tirou o jeito antigo de trocar o ambiente de uma função (o setfenv). No Lua 5.1 e no LuaJIT (Neovim, LÖVE), o _ENV é só um nome qualquer, que não existe: luajit e5.lua → luajit: e5.lua:3: attempt to index global '_ENV' (a nil value). Lá, o ambiente se troca com setfenv(f, ambiente), e o loadstring faz o papel do load com texto. No 5.5, setfenv e getfenv não existem (print(setfenv, getfenv) mostrou nil nil). Veja as diferenças entre as versões.

Quando dá errado

Trocou o _ENV e perdeu o print 
$ lua e7.lua
lua: e7.lua:2: attempt to call a nil value (global 'print')
stack traceback:
	e7.lua:2: in main chunk
	[C]: in ?

Depois de local _ENV = {}, todo nome solto é procurado na tabela nova, inclusive print, string, math. Como consertar: guarde o que precisar em variáveis locais antes da troca (local print = print), ou ponha na tabela nova (local _ENV = { print = print }).

O código carregado não acha uma variável sua 
local formula = "return largura * altura"
local medidas = { largura = 4, altura = 5 }
local calcula = assert(load(formula, "formula", "t"))
print("Área: " .. calcula())

$ lua m_env2.lua
lua: [string "formula"]:1: attempt to perform arithmetic on a nil value (global 'largura')
stack traceback:
	[string "formula"]:1: in local 'calcula'
	m_env2.lua:4: in main chunk
	[C]: in ?

Linha por linha:

[string "formula"]:1:
O erro foi no pedaço de código chamado formula (o texto que você deu ao load), na linha 1 dele.
attempt to perform arithmetic on a nil value (global 'largura')
"Tentativa de fazer conta com um valor nil (a global 'largura')". Para o código carregado, largura é um nome solto, procurado no ambiente dele. Sem o quarto argumento, o ambiente é a tabela das globais, onde não há largura.
in local 'calcula' / m_env2.lua:4
O pedaço foi chamado pela função guardada na variável local calcula, na linha 4 do seu arquivo.

Um código carregado nunca enxerga as variáveis local de quem o carregou. A missão final conserta isso.

O texto tem erro de sintaxe e você chamou o resultado mesmo assim 
local f, erro = load("x = = 1", "receita", "t", {})
print(f, erro)

$ lua e10.lua
nil	[string "receita"]:1: unexpected symbol near '='

Com erro de sintaxe, o load não dá erro: ele devolve nil e a mensagem. Se o programa fizesse f() sem conferir, viria um attempt to call a nil value. Como consertar: confira o primeiro valor (if not f then … end) ou embrulhe no assert(load(…)).

Missão final: a fórmula enxerga as medidas

Missão: a fórmula é um texto carregado com load, e ela não acha largura (rode para ver o erro da seção "Quando dá errado"). Dê a tabela medidas como ambiente da fórmula, no quarto argumento do load, para sair Área: 20.

local formula = "return largura * altura"
local medidas = { largura = 4, altura = 5 }
local calcula = assert(load(formula, "formula", "t"))
print("Área: " .. calcula())

local formula = "return largura * altura"
local medidas = { largura = 4, altura = 5 }
local calcula = assert(load(formula, "formula", "t", medidas))
print("Área: " .. calcula())

Depois, por curiosidade: troque a fórmula por "return math.floor(largura / altura)". Vai dar erro, porque o ambiente medidas não tem math. Como você daria só o math à fórmula?

Resumo

  • As globais moram numa tabela comum. _G é um campo dela que aponta para ela mesma: _G.nome e _G["nome"] são a global nome.
  • Todo nome solto x vira _ENV.x. Normalmente _ENV é a tabela das globais, mas ele é só uma variável: local _ENV = t troca o ambiente daquele bloco.
  • load(codigo, nome, "t", ambiente) roda o texto enxergando só o ambiente: é a base de uma caixa de areia. Use "t" e pcall, e lembre que ela não protege contra laços infinitos.
  • O código carregado nunca vê as variáveis local de quem o carregou.
  • Uma metatabela em _G pega globais criadas por engano, ao rodar; no 5.5, a declaração global faz isso antes de rodar.
  • O _ENV é do Lua 5.2 em diante; no 5.1 e no LuaJIT, use setfenv.
