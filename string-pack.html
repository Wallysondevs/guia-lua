Lua string.pack

Até aqui, todo arquivo que você gravou era texto: dá para abrir no editor e ler. Mas muitos arquivos do computador não são assim: imagens, músicas, o "save" de um jogo, os dados de um sensor. Eles guardam os números do jeito que o computador guarda na memória, em bytes, e por isso se chamam arquivos binários. Para criar e ler esses bytes, o Lua tem três funções: string.pack ("empacotar"), string.unpack ("desempacotar") e string.packsize ("tamanho do pacote").

Você vai aprender
  • A diferença entre guardar um número como texto e como binário.
  • Como string.pack transforma valores em bytes, com um formato ("i4", "d", "z"…).
  • Como ver esses bytes, um por um, em hexadecimal.
  • Como string.unpack faz o caminho de volta, e o que é a posição que ele devolve.
  • Como string.packsize diz o tamanho de um registro.
  • A ordem dos bytes (< e >) e por que ela importa.
  • Como gravar e ler um arquivo binário, e os erros reais mais comuns.

Os programas desta aula rodaram no Lua 5.5 da máquina da Ana (usuária ana, computador notebook), com lua arquivo.lua. Antes, é bom conhecer io.open, string.format e string.byte.

A ideia: o formulário de quadradinhos

Lembra daqueles formulários de papel com um quadradinho para cada letra? "Nome: □□□□□□□□□□", "Idade: □□", "CEP: □□□□□-□□□". Cada campo tem um número fixo de quadradinhos, sempre no mesmo lugar. Quem lê o formulário sabe exatamente onde começa cada campo, sem precisar procurar vírgulas nem espaços.

Um arquivo binário é um formulário assim. O "molde" que diz quantos quadradinhos (bytes) cada campo tem e em que ordem eles vêm se chama formato. Com o formato "i4 d B", por exemplo, você combina: "primeiro um inteiro de 4 bytes, depois um número com vírgula de 8 bytes, depois um número pequeno de 1 byte". O string.pack preenche o formulário; o string.unpack lê de volta, usando o mesmo molde.

1. Texto × binário: o número 100

O número 100, escrito como texto, são três caracteres: "1", "0" e "0". Escrito em binário como um inteiro de 4 bytes, são 4 bytes que formam o número. Para ver os bytes, este programa tem uma função hex que mostra cada byte em hexadecimal (base 16, de 00 a FF; veja string.format, que faz isso com o %02X):

local function hex(s)
  local partes = {}
  for i = 1, #s do
    partes[i] = string.format("%02X", s:byte(i))
  end
  return table.concat(partes, " ")
end

local como_texto = tostring(100)
local como_binario = string.pack("i4", 100)
print("Texto:  ", #como_texto, "bytes:", hex(como_texto))
print("Binário:", #como_binario, "bytes:", hex(como_binario))

$ lua texto_binario.lua
Texto:  	3	bytes:	31 30 30
Binário:	4	bytes:	64 00 00 00
local function hex(s)
Uma ajudante que vamos usar a aula toda: passa por cada byte do texto s (s:byte(i) dá o número do byte, de 0 a 255) e escreve esse número com 2 dígitos hexadecimais.
31 30 30
O texto "100": 31 é o código do caractere "1" e 30 é o do "0". Três bytes.
string.pack("i4", 100)
Empacota o número 100 como um inteiro (i) de 4 bytes (4). O resultado é uma string do Lua, mas não é um texto para ler: é só um saquinho de 4 bytes.
64 00 00 00
100 em hexadecimal é 64. Os outros três bytes são zero. O byte "pequeno" veio primeiro (a seção 4 explica essa ordem).

Para o número 100 o binário até ficou maior (4 bytes contra 3). Mas pense em 2 bilhões: como texto são 10 caracteres; em "i4", continuam sendo 4 bytes. E o mais importante: num formato binário, todo número ocupa o mesmo espaço, então cada campo fica sempre no mesmo lugar, como no formulário.

A "string" do Lua guarda qualquer byte

No Lua, uma string é uma sequência de bytes, qualquer byte, inclusive o zero. É por isso que o string.pack pode devolver uma string: ela serve de "saquinho de bytes". O # conta os bytes (veja O Operador de Tamanho). Só não adianta mandar print nela: sairiam caracteres estranhos. Para ver, use a hex.

2. Os formatos mais usados

Cada letra do formato é um tipo de campo. Este programa empacota um valor de cada tipo e mostra os bytes:

local function hex(s)
  local partes = {}
  for i = 1, #s do
    partes[i] = string.format("%02X", s:byte(i))
  end
  return table.concat(partes, " ")
end

print("B   255     ", hex(string.pack("B", 255)))
print("b   -1      ", hex(string.pack("b", -1)))
print("h   1000    ", hex(string.pack("h", 1000)))
print("i4  100000  ", hex(string.pack("i4", 100000)))
print("j   1       ", hex(string.pack("j", 1)))
print("d   1.5     ", hex(string.pack("d", 1.5)))
print("f   1.5     ", hex(string.pack("f", 1.5)))
print("z   Ana     ", hex(string.pack("z", "Ana")))

3. O caminho de volta: string.unpack

string.unpack(formato, dados) lê os bytes com o mesmo formato e devolve os valores. E devolve mais um: a posição do primeiro byte que ele não leu, onde começaria o próximo campo:

local dados = string.pack("i4", 100)
local numero, proxima = string.unpack("i4", dados)
print(numero, proxima)

local registro = string.pack("<z B d", "Bia", 9, 8.5)
print(#registro)
local nome, idade, nota, fim = string.unpack("<z B d", registro)
print(nome, idade, nota, fim)

$ lua desempacotar.lua
100	5
13
Bia	9	8.5	14
100 5
O número de volta, e a posição 5: ele leu os bytes 1, 2, 3 e 4; o próximo seria o 5.
"<z B d"
Um formato com três campos, separados por espaço (os espaços são só para ler melhor; o Lua os ignora): o nome terminado em zero, a idade em 1 byte e a nota em 8 bytes. O < do começo fixa a ordem dos bytes (seção 4).
13
4 bytes do "Bia" com o zero + 1 da idade + 8 da nota = 13.
nome, idade, nota, fim
Um valor para cada campo, na ordem, e no fim a posição seguinte (14 = 13 + 1). Igualzinho a uma função com vários retornos.

Para ler a partir de um lugar no meio, passe a posição como terceiro argumento: string.unpack("i4", dados, 5) começa no byte 5. É assim que se lê um campo depois do outro (a seção 6 usa isso).

4. A ordem dos bytes: < e >

Um número de vários bytes pode ser gravado começando pelo byte "pequeno" ou pelo "grande", como uma data que pode ser escrita 18/10/2026 ou 2026/10/18. Os dois jeitos existem de verdade:

local function hex(s)
  local partes = {}
  for i = 1, #s do
    partes[i] = string.format("%02X", s:byte(i))
  end
  return table.concat(partes, " ")
end

print("<i4", hex(string.pack("<i4", 1000)))
print(">i4", hex(string.pack(">i4", 1000)))
print("=i4", hex(string.pack("=i4", 1000)))
print(string.unpack("<i4", string.pack(">i4", 1000)))

A última linha mostra o perigo: gravar com > e ler com < não dá erro nenhum, só um número errado (-402456576 em vez de 1000). Por isso, num arquivo que vai para outro computador, escreva a ordem no formato (< ou >) e use o mesmo formato para gravar e para ler.

5. O tamanho de um registro: string.packsize

string.packsize(formato) diz quantos bytes um formato ocupa, sem empacotar nada:

print(string.packsize("i4"))
print(string.packsize("B"))
print(string.packsize("d"))
print(string.packsize("<i4 B d"))
print(string.packsize("!<i4 B d"))
print(string.packsize("j"), string.packsize("n"))

$ lua tamanho.lua
4
1
8
13
16
8	8

"<i4 B d" dá 4 + 1 + 8 = 13. Com um ! na frente, o Lua alinha cada campo, como um programa em C faria: ele põe bytes de enchimento para o d começar numa posição múltipla de 8, e o total vira 16. Você só precisa do ! para conversar com programas em C; para os seus arquivos, sem ele fica menor.

O packsize só funciona com campos de tamanho fixo: com z ou s1 (texto de tamanho variável) ele dá erro, porque o tamanho depende do texto.

Missão: o registro da Bia usa i4 (4 bytes) para a idade, mas uma idade cabe folgada em 1 byte (0 a 255). Troque o formato da idade para o de 1 byte sem sinal e veja o registro encolher.

local FORMATO = "<z i4 d"   -- nome, idade, nota
local registro = string.pack(FORMATO, "Bia", 9, 8.5)
print("Tamanho do registro: " .. #registro .. " bytes")
print(string.unpack(FORMATO, registro))

6. Gravando um arquivo binário

A lojinha da Ana guarda o estoque num arquivo binário: para cada produto, o código (i4), o preço (d) e a quantidade (B). Cada produto vira um registro de 13 bytes, um atrás do outro:

local FORMATO = "<i4 d B"   -- código, preço, quantidade

local produtos = {
  { codigo = 101, preco = 4.5,  quantidade = 12 },
  { codigo = 102, preco = 12.9, quantidade = 3 },
  { codigo = 103, preco = 7.25, quantidade = 30 },
}

local f = assert(io.open("estoque.bin", "wb"))
for _, p in ipairs(produtos) do
  f:write(string.pack(FORMATO, p.codigo, p.preco, p.quantidade))
end
f:close()
print("Gravei " .. #produtos .. " produtos de " .. string.packsize(FORMATO) .. " bytes cada")

$ lua gravar.lua
Gravei 3 produtos de 13 bytes cada
$ ls -l estoque.bin
-rw-rw-r-- 1 ana ana 39 Oct 18 16:41 estoque.bin
local FORMATO = "<i4 d B"
O molde do registro, numa variável só. Quem grava e quem lê usam a mesma; se mudar, muda nos dois lugares de uma vez.
io.open("estoque.bin", "wb")
Abre para escrever (w) em modo binário (b). No Linux, o b não muda nada; no Windows, sem ele, o sistema mexe nos bytes de quebra de linha e estraga o arquivo. Escreva sempre: não custa nada. O assert para o programa com a mensagem do sistema se o arquivo não abrir.
f:write(string.pack(…))
Grava os 13 bytes de cada produto. O write aceita a string de bytes como aceita qualquer texto.
39
O ls -l confirma: 3 produtos × 13 bytes = 39 bytes.

Abrir esse arquivo num editor de texto mostraria lixo. Para olhar os bytes, o Linux tem o hexdump -C:

$ hexdump -C estoque.bin
00000000  65 00 00 00 00 00 00 00  00 00 12 40 0c 66 00 00  |e..........@.f..|
00000010  00 cd cc cc cc cc cc 29  40 03 67 00 00 00 00 00  |.......)@.g.....|
00000020  00 00 00 00 1d 40 1e                              |.....@.|

À esquerda, a posição (em hexadecimal); no meio, os bytes; à direita, os bytes que por acaso são letras. Dá para achar os campos: 65 00 00 00 é o código 101 (hexadecimal 65), os 8 bytes seguintes são o preço 4.5, e o 0c é a quantidade 12. Logo depois começa o produto 102 (66).

7. Lendo o arquivo de volta

Como cada registro tem exatamente 13 bytes, dá para ler de 13 em 13 com f:read(n), que lê n bytes (e devolve nil no fim do arquivo):

local FORMATO = "<i4 d B"
local TAMANHO = string.packsize(FORMATO)

local f = assert(io.open("estoque.bin", "rb"))
while true do
  local pedaco = f:read(TAMANHO)
  if not pedaco then break end
  local codigo, preco, quantidade = string.unpack(FORMATO, pedaco)
  print(string.format("%d  R$ %6.2f  x%d", codigo, preco, quantidade))
end
f:close()

$ lua ler.lua
101  R$   4.50  x12
102  R$  12.90  x3
103  R$   7.25  x30

Os três produtos voltaram iguaizinhos. O "rb" é "ler em modo binário". Repare que o preço 12.9 voltou como 12.90: o formato d guarda o número com vírgula do Lua sem perder nada.

Outro jeito: ler tudo e andar com a posição

Também dá para ler o arquivo inteiro com f:read("a") e ir desempacotando com a posição que o unpack devolve:

local FORMATO = "<i4 d B"

local f = assert(io.open("estoque.bin", "rb"))
local dados = f:read("a")
f:close()

local pos = 1
local total = 0
while pos <= #dados do
  local codigo, preco, quantidade
  codigo, preco, quantidade, pos = string.unpack(FORMATO, dados, pos)
  total = total + quantidade
end
print("Bytes lidos: " .. #dados)
print("Unidades no estoque: " .. total)

$ lua ler_tudo.lua
Bytes lidos: 39
Unidades no estoque: 45

A cada volta, o unpack lê um registro a partir de pos e devolve a posição do próximo, que vai direto para a variável pos. Quando pos passa do tamanho dos dados, acabou. Esse jeito também funciona com campos de tamanho variável (z, s1), em que não dá para saber o tamanho de antemão.

Formas diferentes de fazer a mesma coisa

O mesmo estoque poderia ser guardado como texto, uma linha por produto (101;4.5;12), e lido com io.lines. Qual escolher?

SituaçãoQual usar
Um arquivo que pessoas vão abrir, ler ou editar (lista de compras, CSV de notas)Texto (Escrevendo Arquivos)
Ler ou criar um formato que já existe e é binário (imagem, som, protocolo de rede, "save" de jogo)string.pack/unpack, com o formato da especificação
Muitos números, onde espaço e velocidade importamBinário, com registros de tamanho fixo
Registros de tamanho fixof:read(string.packsize(FORMATO)) em laço

Outras versões

string.pack, string.unpack e string.packsize existem desde o Lua 5.3 (no lab, também no lua5.4). No Lua 5.1 e no LuaJIT elas não existem: luajit -e 'print(string.pack)' mostra nil, e quem usa o LuaJIT recorre a outras ferramentas (como a biblioteca ffi dele). Veja as diferenças entre as versões.

Como consertar: escolha um formato maior (H vai até 65535, i4 até uns 2 bilhões).

Número com vírgula num campo de inteiro 
local preco = 4.5
local dados = string.pack("i4", preco)
print(#dados)

	[C]: in field 'pack'

"O número não tem representação inteira": 4.5 não é um inteiro, e o i4 só guarda inteiros. O Lua não arredonda escondido. Como consertar: use d para números com vírgula (ou guarde o preço em centavos, 450, num inteiro).

Dados curtos demais 
local dados = string.pack("i2", 7)
local a, b = string.unpack("i2 i2", dados)
print(a, b)

$ lua curto.lua
lua: curto.lua:2: bad argument #2 to 'unpack' (data string too short)
stack traceback:
	[C]: in field 'unpack'
	curto.lua:2: in main chunk
	[C]: in ?

"A string de dados é curta demais": o formato pede 4 bytes (dois i2), e só havia 2. Acontece quando o formato de leitura não é o mesmo da gravação, ou quando o arquivo acabou no meio de um registro (gravação interrompida). Como consertar: use o mesmo formato dos dois lados, e confira o tamanho antes (#pedaco == TAMANHO).

Letra que não existe no formato 
print(string.packsize("i4 w"))

$ lua letra.lua

stack traceback:
	[C]: in field 'packsize'
	letra.lua:1: in main chunk
	[C]: in ?

"Opção de formato inválida 'w'". Não existe o formato w. Confira as letras na tabela da seção 2 (maiúscula e minúscula são diferentes: B é sem sinal, b é com sinal).

O erro que não dá erro: formato trocado na leitura 
local FORMATO = ">i4 d B"   -- errado: o arquivo foi gravado com "<"
local f = assert(io.open("estoque.bin", "rb"))
local pedaco = f:read(string.packsize(FORMATO))
f:close()
print(string.unpack(FORMATO, pedaco))

$ lua trocado.lua
1694498816	2.3082746973703e-320	12	14

Nenhuma mensagem de erro, só números absurdos: o código 101 virou 1694498816 e o preço virou um número minúsculo. Para o unpack, bytes são só bytes; quem sabe o que eles querem dizer é o formato. Só a quantidade (12) saiu certa, porque um campo de 1 byte não tem ordem. Como consertar: o mesmo FORMATO na gravação e na leitura. Se o número que sai é absurdo, desconfie primeiro da ordem dos bytes e do tamanho dos campos.

Resumo

  • Um arquivo binário guarda os valores como bytes, em campos de tamanho combinado; o formato é o molde desses campos.
  • string.pack(fmt, …) transforma valores em uma string de bytes; string.unpack(fmt, dados, pos) faz o caminho de volta e devolve também a próxima posição; string.packsize(fmt) dá o tamanho.
  • Formatos comuns: B (0–255), h, i4, j, d, f, z, s1. Maiúscula = sem sinal.
  • Escreva a ordem dos bytes no formato (< ou >) e use o mesmo formato para gravar e ler: formato trocado não dá erro, dá número errado.
  • Arquivos binários se abrem com "wb" e "rb"; para ver os bytes, hexdump -C.
  • Essas funções existem desde o Lua 5.3; não existem no 5.1 nem no LuaJIT.
