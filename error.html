Lua error: Lançando Erros

Até agora, os erros apareciam sozinhos: o Lua tentava somar um nil e parava. Mas muitas vezes é você quem sabe que algo está errado, mesmo que o Lua ache tudo normal: um saque maior que o saldo, uma idade negativa, um produto que não existe no estoque. Para esses casos existe a função error ("erro"): ela para o programa na hora, com uma mensagem escrita por você, no mesmo formato das mensagens do Lua. Dizemos que o programa lança um erro.

Você vai aprender
  • Como usar error("mensagem") para parar o programa quando um valor não faz sentido.
  • O que a mensagem e o stack traceback mostram, incluindo a linha [C]: in global 'error'.
  • O nível do erro (error(msg, 2), error(msg, 0)) e como ele muda a linha que aparece na mensagem.
  • Mensagens com valores dentro, usando string.format.
  • Lançar uma tabela como erro (e o que o lua mostra quando ninguém a captura).
  • Quando usar error e quando é melhor devolver nil, "mensagem".

Todos os programas desta aula rodaram no Lua 5.5 da máquina da Ana (usuária ana, computador notebook) com lua arquivo.lua. Para entender as mensagens, vale ter lido Lendo uma Mensagem de Erro.

A ideia: o alarme do caixa

Na padaria da Ana, o caixa tem um botão de alarme. Se alguém tenta pagar com uma nota falsa, o funcionário não continua o atendimento como se nada fosse: ele aperta o botão, o atendimento para, e o gerente vem ver o que houve, com um bilhete explicando o problema.

O error é esse botão. Quando uma função percebe que recebeu algo impossível, em vez de continuar e produzir uma resposta errada (que pode estragar o resto do programa sem ninguém perceber), ela "aperta o alarme": o programa para, e a mensagem diz o que aconteceu e onde. Quem é o "gerente" que pode atender o alarme sem fechar a loja? É o pcall, assunto da próxima aula.

1. O problema: o Lua não reclama de tudo

Uma função de dividir, do jeito mais simples:

local function dividir(a, b)
  return a / b
end
print(dividir(10, 2))
print(dividir(7, 0))
print(dividir(0, 0))

$ lua dividir0.lua
5.0
inf
-nan

Nenhum erro. Dividir por zero com / dá inf (de infinity, "infinito") e 0 / 0 dá -nan (not a number, "não é um número"). São valores válidos para o Lua, mas, para a conta da padaria, são lixo: se esse inf entrar no total do dia, o total vira inf também, e ninguém sabe de onde veio. (Só a divisão inteira 7 // 0 dá erro: attempt to divide by zero; veja Divisão.) É melhor a função reclamar na hora.

2. O primeiro error

A Ana tem R$ 100 na conta. Sacar mais do que isso não pode:

local saldo = 100

local function sacar(valor)
  if valor > saldo then
    error("saldo insuficiente")
  end
  saldo = saldo - valor
  print("Sacou " .. valor .. ", saldo agora: " .. saldo)
end

sacar(30)
sacar(50)
sacar(40)
print("Fim do dia")

A verificação: o saque é possível?
error("saldo insuficiente")
Se não for, lança um erro com essa mensagem. O error não volta: nada depois dele, nesta função ou no resto do programa, é executado.
saldo = saldo - valor
Só chega aqui quem passou na verificação. Por isso o saldo nunca fica negativo.
$ lua sacar.lua
Sacou 30, saldo agora: 70
Sacou 50, saldo agora: 20
lua: sacar.lua:5: saldo insuficiente
stack traceback:
	[C]: in global 'error'
	sacar.lua:5: in local 'sacar'
	sacar.lua:13: in main chunk
	[C]: in ?
$ echo $?
1

Os dois primeiros saques funcionaram. O terceiro (40, com só 20 de saldo) disparou o alarme. Linha por linha:

lua: sacar.lua:5: saldo insuficiente
O formato de sempre, arquivo:linha: mensagem. A mensagem é a sua; o sacar.lua:5: o error acrescentou sozinho, dizendo a linha do error.
[C]: in global 'error'
A primeira linha do rastro é a própria função error (escrita em C). Ela aparece em todo erro lançado assim.
sacar.lua:5: in local 'sacar'
Quem chamou o error: a linha 5, dentro da função sacar.
sacar.lua:13: in main chunk
Quem chamou o sacar: a linha 13, o sacar(40). É o saque problemático.
echo $? → 1
O programa terminou com erro. O Fim do dia nunca apareceu.

Para o Lua, não há diferença entre um erro que ele mesmo encontrou e um erro lançado por você: os dois param o programa, mostram a mensagem e o rastro, e dão código de saída 1. E os dois podem ser capturados com pcall.

Missão: faça a função dividir lançar um erro com a mensagem divisão por zero quando o b for 0, em vez de devolver inf. A primeira divisão (10 / 2) deve continuar mostrando 5.0.

local function dividir(a, b)
  return a / b
end
print(dividir(10, 2))
print(dividir(7, 0))

local function dividir(a, b)
  if b == 0 then
    error("divisão por zero")
  end
  return a / b
end
print(dividir(10, 2))
print(dividir(7, 0))

3. Mensagens com os valores dentro

"Saldo insuficiente" ajuda, mas "só temos 0 de leite, pediram 2" ajuda muito mais. Monte a mensagem com .. ou, melhor, com string.format:

local function dividir(a, b)
  if b == 0 then
    error("divisão por zero: " .. a .. " / " .. b)
  end
  return a / b
end
print(dividir(10, 2))
print(dividir(7, 0))

$ lua concat_err.lua
5.0
lua: concat_err.lua:3: divisão por zero: 7 / 0
stack traceback:
	[C]: in global 'error'
	concat_err.lua:3: in local 'dividir'
	concat_err.lua:8: in main chunk
	[C]: in ?

Com string.format, o %q põe o texto entre aspas (bom para mostrar exatamente o que veio, inclusive espaços), e o %d mostra um inteiro:

local estoque = { pao = 10, leite = 0 }
local function vender(produto, qtd)
  local tem = estoque[produto]
  if tem == nil then
    error(string.format("produto desconhecido: %q", produto), 2)
  end
  estoque[produto] = tem - qtd
end
vender("bolo", 1)

$ lua formatado2.lua
lua: formatado2.lua:9: produto desconhecido: "bolo"
stack traceback:
	[C]: in global 'error'
	formatado2.lua:5: in local 'vender'
	formatado2.lua:9: in main chunk
	[C]: in ?

Repare num detalhe: o error está na linha 5, mas a mensagem diz formatado2.lua:9:. É por causa daquele 2 no fim do error(…, 2). Ele é o assunto da próxima seção, e é a parte mais útil do error.

4. O nível do erro: de quem é a culpa?

A função cadastrar só aceita idade em número. Quando alguém passa "trinta", de quem é a culpa? Da função cadastrar, que está certinha? Não: é de quem chamou com o valor errado. O segundo argumento do error, o nível, diz qual linha a mensagem deve apontar.

Nível 1 (o padrão): a linha do próprio error

local function cadastrar(idade)
  if type(idade) ~= "number" then
    error("a idade precisa ser um número")
  end
  print("Cadastrada com " .. idade .. " anos")
end

cadastrar(30)
cadastrar("trinta")

$ lua nivel1.lua
Cadastrada com 30 anos
lua: nivel1.lua:3: a idade precisa ser um número
stack traceback:
	[C]: in global 'error'
	nivel1.lua:3: in local 'cadastrar'
	nivel1.lua:9: in main chunk
	[C]: in ?

Sem o segundo argumento, o nível é 1: a mensagem aponta a linha 3, onde está o error. Quem lê vai olhar a linha 3, ver que ela está certa, e só descobrir no rastro que o culpado é a linha 9.

Nível 2: a linha de quem chamou a função

local function cadastrar(idade)
  if type(idade) ~= "number" then
    error("a idade precisa ser um número", 2)
  end
  print("Cadastrada com " .. idade .. " anos")
end

cadastrar(30)
cadastrar("trinta")

$ lua nivel2.lua
Cadastrada com 30 anos
lua: nivel2.lua:9: a idade precisa ser um número
stack traceback:
	[C]: in global 'error'
	nivel2.lua:3: in local 'cadastrar'
	nivel2.lua:9: in main chunk
	[C]: in ?

Agora a mensagem aponta a linha 9, o cadastrar("trinta"): exatamente onde está o engano. O rastro é o mesmo; só a primeira linha mudou. É assim que as funções prontas do Lua fazem: quando você escreve table.insert(nil, 1), o erro aponta a sua linha, não uma linha de dentro do table.insert.

Regra prática

Se o erro é "quem me chamou passou um valor errado" (validação de argumentos), use nível 2. Se o erro é "algo deu errado aqui dentro", deixe o nível 1.

Nível 3, 4…: subindo mais

Se a verificação está numa função auxiliar, chamada por outra, o nível 2 apontaria a função do meio. Cada número a mais sobe um degrau no rastro:

local function validar(idade)
  if type(idade) ~= "number" then
    error("a idade precisa ser um número", 3)
  end
end

local function cadastrar(idade)
  validar(idade)
  print("Cadastrada com " .. idade .. " anos")
end

cadastrar(30)
cadastrar("trinta")

$ lua nivel3.lua
Cadastrada com 30 anos
lua: nivel3.lua:13: a idade precisa ser um número
stack traceback:
	[C]: in global 'error'
	nivel3.lua:3: in upvalue 'validar'
	nivel3.lua:8: in local 'cadastrar'
	nivel3.lua:13: in main chunk
	[C]: in ?

Nível 1 seria a linha 3 (o error), nível 2 a linha 8 (o validar(idade)), nível 3 a linha 13 (o cadastrar("trinta")). Compare com o rastro: é contar as linhas de cima para baixo, pulando o [C]: in global 'error'.

Nível 0: sem posição nenhuma

local function cadastrar(idade)
  if type(idade) ~= "number" then
    error("a idade precisa ser um número", 0)
  end
  print("Cadastrada com " .. idade .. " anos")
end

cadastrar(30)
cadastrar("trinta")

$ lua nivel0.lua
Cadastrada com 30 anos
lua: a idade precisa ser um número
stack traceback:
	[C]: in global 'error'
	nivel0.lua:3: in local 'cadastrar'
	nivel0.lua:9: in main chunk
	[C]: in ?

Com nível 0, o error não acrescenta arquivo:linha:. Serve quando a mensagem vai ser mostrada para quem usa o programa (não para quem o escreveu): "a idade precisa ser um número" é mais amigável que "nivel0.lua:9: a idade…". Você vai ver esse uso com o pcall, que captura a mensagem para mostrá-la do seu jeito.

5. Lançando uma tabela

A mensagem de erro não precisa ser um texto: o error aceita qualquer valor. Uma tabela permite carregar várias informações juntas, como um código e uma descrição:

error({ codigo = 404, mensagem = "produto não encontrado" })

$ lua tabela.lua
lua: (error object is a table value)
stack traceback:
	[C]: in global 'error'
	tabela.lua:1: in main chunk
	[C]: in ?

"(O objeto de erro é um valor do tipo tabela)". O lua não sabe transformar uma tabela em texto, então só avisa o tipo. E repare: não há tabela.lua:1: no começo. O error só acrescenta a posição quando a mensagem é um texto. A tabela faz sentido mesmo é quando alguém a captura com pcall e lê os campos (erro.codigo), como você vai ver na próxima aula.

Se a tabela tiver um metamétodo __tostring, o lua o usa para escrever a mensagem:

local erro = setmetatable(
  { codigo = 404, mensagem = "produto não encontrado" },
  { __tostring = function (e) return "Erro " .. e.codigo .. ": " .. e.mensagem end }
)
error(erro)

$ lua tabela_ts.lua
lua: Erro 404: produto não encontrado
$ echo $?
1

Desta vez, saiu só a mensagem, sem stack traceback: quando o objeto de erro tem __tostring, o lua usa o texto dele e não acrescenta o rastro. Outros valores, conferidos no lab:

CódigoO lua mostrou
error(42)lua: 42 (com o rastro; sem a posição, porque 42 não é texto)
error()lua: (error object is a nil value) (com o rastro)
error({…})lua: (error object is a table value) (com o rastro)
error(tabela_com___tostring)o texto do __tostring, sem rastro

Formas diferentes: error ou devolver nil, "mensagem"?

No Lua existe outro costume para avisar que algo deu errado, sem parar nada: a função devolve nil e, como segundo valor, uma mensagem. É o que as funções prontas de arquivos fazem:

print(io.open("nao_existe.txt"))
print(tonumber("abc"))

$ lua io_compara.lua
nil	nao_existe.txt: No such file or directory	2
nil

O io.open não conseguiu abrir e devolveu nil, a mensagem ("arquivo ou pasta inexistente") e um número de erro do sistema. O tonumber devolveu só nil. Ninguém parou. A sua função pode fazer igual:

local saldo = 100

local function sacar(valor)
  if valor > saldo then
    return nil, "saldo insuficiente"
  end
  saldo = saldo - valor
  return saldo
end

print(sacar(30))
print(sacar(500))
local novo, problema = sacar(500)
if not novo then
  print("Não deu: " .. problema)
end
print("O programa continua")

$ lua retorno_nil.lua
70
nil	saldo insuficiente
Não deu: saldo insuficiente
O programa continua

Quando dá errado

A mensagem aponta a linha do error, e ela está certa

É o nível 1 da seção 4 (nivel1.lua:3:). Não há nada para consertar na linha 3: desça pelo rastro até a linha in main chunk (ou a primeira chamada sua) para ver quem passou o valor errado. Se a função é sua, troque para error(msg, 2) e a mensagem passa a apontar o lugar certo.

A mensagem de erro deu erro

Montar a mensagem com .. usando um valor nil dá um erro antes do seu, e a mensagem que aparece é outra. Se o error("produto desconhecido: " .. produto) receber produto igual a nil, o que aparece é outra coisa:

local function vender(produto)
  error("produto desconhecido: " .. produto)
end
vender(nil)

$ lua msgnil.lua
lua: msgnil.lua:2: attempt to concatenate a nil value (local 'produto')
stack traceback:
	msgnil.lua:2: in local 'vender'
	msgnil.lua:4: in main chunk
	[C]: in ?

Repare que nem há [C]: in global 'error' no rastro: o error nem chegou a ser chamado. Com string.format("produto desconhecido: %q", produto) (ou tostring(produto)), o nil vira o texto nil e a sua mensagem sai inteira: lua: msgnil2.lua:2: produto desconhecido: nil. O mesmo cuidado vale para o assert.

Lançou uma tabela e só apareceu (error object is a table value)

A tabela de erro foi feita para ser capturada (pcall) e lida pelos campos. Se ninguém a captura, o lua não tem como mostrar o conteúdo. Para o terminal, use texto, ou dê à tabela um __tostring (seção 5).

Usou error para algo que não é erro

Um usuário digitar "trinta" no lugar de 30 não é um defeito do programa: é algo que vai acontecer. Se a função de ler a idade lançar error, o programa fecha na cara do usuário. Para entradas do usuário, prefira devolver nil, "mensagem" e perguntar de novo (ou capture com pcall).

Resumo

  • error(mensagem) para o programa na hora, como um erro do próprio Lua: mensagem, stack traceback (começando com [C]: in global 'error') e código de saída 1.
  • Use-o quando um valor não faz sentido e continuar produziria lixo (saque maior que o saldo, divisão por zero).
  • O segundo argumento é o nível: 1 (padrão) aponta a linha do error, 2 a de quem chamou a função, 0 não mostra posição.
  • Mensagens com valores: string.format (o %q mostra o texto entre aspas e não quebra com nil).
  • O erro pode ser uma tabela; sem captura, o lua só diz (error object is a table value).
  • Para problemas esperados (arquivo que não existe, entrada do usuário), prefira return nil, "mensagem". Para capturar um erro, a próxima aula: pcall.
