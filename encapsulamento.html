Lua Privacidade com Closures

Nas classes da aula Classes com Metatabelas, o saldo da conta é um campo comum: qualquer linha do programa pode escrever conta_ana.saldo = -500, e o método depositar, com todas as suas regras, nem fica sabendo. Proteger os dados de um objeto para que só os métodos dele mexam neles se chama encapsulamento (de "cápsula"). O Lua não tem uma palavra private, mas tem uma ferramenta que faz isso muito bem: as closures.

Você vai aprender
  • Por que um campo aberto (conta.saldo) é perigoso, com os erros reais que aparecem longe da causa.
  • A convenção do sublinhado (_saldo) e o que ela não protege.
  • A conta com closures: o saldo vira uma variável local que só as funções da conta enxergam.
  • Por que esses objetos usam ponto (ana.depositar(50)), e não dois-pontos.
  • O estoque com a lista de produtos privada, e como entregar uma cópia.
  • Closures × metatabelas: quando usar cada uma.
  • Os erros reais: o dois-pontos, a função sobrescrita, e como travar a tabela com __newindex.

Todos os programas rodaram no Lua 5.5 da máquina da Ana (usuária ana, computador notebook) com lua arquivo.lua. Revise antes Closures (é a base desta aula), Escopo e Blocos e Classes.

A ideia: o caixa eletrônico

No caixa eletrônico, a Ana não abre o cofre do banco para pôr o dinheiro lá dentro. Ela usa os botões: "depositar", "sacar", "ver saldo". O cofre fica atrás da parede, e só as máquinas do banco chegam nele. Por isso o banco consegue garantir as regras: não dá para depositar um valor negativo, nem sacar mais do que tem.

  • O cofre é o dado privado (o saldo).
  • Os botões são as funções públicas (depositar, sacar, saldo), as únicas que chegam no cofre.
  • A parede é o escopo: uma variável local criada dentro de uma função não pode ser vista de fora dela. Mas as funções criadas ali dentro continuam enxergando a variável, mesmo depois: essas funções são as closures.

1. O problema: o saldo aberto

local Conta = {}
Conta.__index = Conta

function Conta.new(titular, saldo)
  return setmetatable({ titular = titular, saldo = saldo or 0 }, Conta)
end

function Conta:depositar(valor)
  if valor <= 0 then error("depósito precisa ser positivo", 2) end
  self.saldo = self.saldo + valor
end

local conta_ana = Conta.new("Ana", 100)
conta_ana.saldo = -500
print(conta_ana.saldo)
conta_ana.saldo = "mil"
conta_ana:depositar(50)

O depositar recusa valores negativos, mas ninguém precisa passar por ele: basta escrever no campo. O Lua aceitou um saldo de −500 sem reclamar.
conta_ana.saldo = "mil"
Pior: um texto no lugar do número. Também aceito, sem erro nessa linha.

"Tentativa de somar uma string com um número". O erro só apareceu depois, dentro do depositar (linha 10), quando ele tentou fazer "mil" + 50. O [C]: in metamethod 'add' é o Lua tentando, sem sucesso, transformar o texto em número (veja Conversão).

O engano foi na linha 16, mas o erro apareceu na 10, dentro de um método que estava certo. Num programa grande, achar quem estragou o saldo pode levar horas. Encapsular é fazer com que só os métodos possam mexer no saldo, e então qualquer saldo errado só pode ter vindo deles.

A convenção do sublinhado

Muita gente escreve os campos "internos" com um sublinhado na frente: self._saldo. É um aviso para pessoas: "não mexa nisto de fora". O Lua não dá a mínima para o sublinhado: conta_ana._saldo = -500 funciona do mesmo jeito. Num time que respeita a convenção, isso basta muitas vezes. Quando você quer uma proteção de verdade, entram as closures.

2. A conta com closures

Em vez de uma classe com metatabela, uma função "fábrica" cria cada conta. O saldo é uma variável local da fábrica, e as funções da conta são criadas lá dentro:

local function nova_conta(titular, saldo_inicial)
  local saldo = saldo_inicial or 0

  local conta = {}

  function conta.depositar(valor)
    if valor <= 0 then
      error("depósito precisa ser positivo", 2)
    end
    saldo = saldo + valor
  end

  function conta.saldo()
    return saldo
  end

  function conta.titular()
    return titular
  end

  return conta
end

local ana = nova_conta("Ana", 100)
local bia = nova_conta("Bia")
ana.depositar(50)
bia.depositar(30)
print(ana.titular(), ana.saldo())
print(bia.titular(), bia.saldo())
print(ana.saldo_inicial, ana.saldo == bia.saldo)
ana.depositar(-10)

$ lua closure.lua

Bia	30
nil	false
lua: closure.lua:31: depósito precisa ser positivo
stack traceback:
	[C]: in global 'error'
	closure.lua:8: in field 'depositar'
	closure.lua:31: in main chunk
	[C]: in ?
local saldo = saldo_inicial or 0
O "cofre". É uma variável local da função nova_conta: fora dela, ninguém consegue escrever o nome saldo e chegar nela.
local conta = {}
A tabela que vai ser devolvida, com os "botões". Ela não tem o saldo dentro: só funções.
function conta.depositar(valor)
Uma closure: foi criada dentro da nova_conta e por isso enxerga o saldo e o titular de lá. Repare no ponto (e não dois-pontos): ela não precisa de self, porque já sabe qual é o seu saldo.
function conta.saldo()
O botão "ver saldo": devolve o valor, mas não deixa mudar. Também o titular virou só leitura.
nova_conta("Ana", 100) e nova_conta("Bia")
Cada chamada da fábrica cria um saldo novo e funções novas presas a ele. A Ana e a Bia têm cofres separados (150 e 30).
ana.saldo_inicial → nil
O parâmetro também ficou lá dentro: de fora, não existe.
ana.saldo == bia.saldo → false
As funções das duas contas são diferentes (cada uma presa ao seu cofre). Numa classe com metatabela, todos os objetos dividem a mesma função.
ana.depositar(-10) → erro
Agora a regra vale de verdade: o único caminho para o saldo passa por ela. O nível 2 do error faz a mensagem apontar para a linha 31, a do pedido errado.

Dá para chegar no saldo de fora?

Vamos tentar. Uma variável saldo do lado de fora é outra variável, que não tem nada a ver com a de dentro, e a tabela da conta só tem as funções:

local function nova_conta(saldo_inicial)
  local saldo = saldo_inicial
  local conta = {}
  function conta.depositar(valor) saldo = saldo + valor end
  function conta.saldo() return saldo end
  return conta
end

local ana = nova_conta(100)
local saldo = 1000000
ana.depositar(50)
print(ana.saldo(), saldo)

local campos = {}
for nome in pairs(ana) do campos[#campos + 1] = nome end
table.sort(campos)
print(table.concat(campos, ", "))

$ lua tentar.lua
150	1000000
depositar, saldo

O milhão ficou na variável de fora; a conta continuou com 150. E percorrer a tabela com pairs mostra só os dois "botões" (depositar e saldo, ordenados com table.sort): o número do saldo não está em lugar nenhum que se possa alcançar.

Missão: acrescente à fábrica um botão function conta.sacar(valor): se valor for maior que saldo, ele mostra "Saldo insuficiente"; senão, tira o valor do saldo. Repare que lá dentro você usa saldo direto, sem self.

local function nova_conta(saldo_inicial)
  local saldo = saldo_inicial or 0
  local conta = {}

  function conta.depositar(valor)
    saldo = saldo + valor
  end

  function conta.saldo()
    return saldo
  end

  -- escreva aqui o conta.sacar(valor)

  return conta
end

local ana = nova_conta(100)
ana.sacar(30)
ana.sacar(500)
print("Saldo: " .. ana.saldo())

local function nova_conta(saldo_inicial)
  local saldo = saldo_inicial or 0
  local conta = {}

  function conta.depositar(valor)
    saldo = saldo + valor
  end

  function conta.saldo()
    return saldo
  end

  function conta.sacar(valor)
    if valor > saldo then
      print("Saldo insuficiente")
    else
      saldo = saldo - valor
    end
  end

  return conta
end

local ana = nova_conta(100)
ana.sacar(30)
ana.sacar(500)
print("Saldo: " .. ana.saldo())

3. O estoque com a lista privada

O dado privado não precisa ser um número. No estoque da padaria, a tabela de produtos inteira fica escondida, e o resto do programa só consegue mexer nela pelas funções de entrada e saída:

local function novo_estoque()
  local produtos = {}
  local estoque = {}

  function estoque.entrada(nome, quantidade)
    produtos[nome] = (produtos[nome] or 0) + quantidade
  end

  function estoque.saida(nome, quantidade)
    local tem = produtos[nome] or 0
    if quantidade > tem then
      return false, "só temos " .. tem .. " de " .. nome
    end
    produtos[nome] = tem - quantidade
    return true
  end

  function estoque.quantidade(nome)
    return produtos[nome] or 0
  end

  function estoque.lista()
    local copia = {}
    for nome, qtd in pairs(produtos) do copia[nome] = qtd end
    return copia
  end

  return estoque
end

local loja = novo_estoque()
loja.entrada("pao", 40)
loja.entrada("leite", 12)
print(loja.saida("pao", 15))
print(loja.saida("leite", 50))
local copia = loja.lista()
copia.pao = 9999
print(loja.quantidade("pao"), copia.pao)
print(loja.produtos)

$ lua estoque.lua
true
false	só temos 12 de leite
25	9999
nil
local produtos = {}
A tabela privada. Ninguém de fora tem uma variável que aponte para ela.
function estoque.lista()
Quem precisa ver todos os produtos recebe uma cópia. Se a função devolvesse a própria produtos, quem recebesse poderia mudá-la à vontade (tabelas são referências), e a privacidade acabaria.
copia.pao = 9999 → 25 9999
Mudar a cópia não muda o estoque: ele continua com 25 pães (40 − 15).
loja.produtos → nil
A tabela de produtos não é um campo da loja.

Formas diferentes de fazer a mesma coisa

Agora você conhece duas formas de fazer objetos no Lua. Elas não brigam: cada uma é melhor numa situação.

Classe com metatabela (Conta.new)Closures (nova_conta)
Onde ficam os dadosEm campos do objeto (self.saldo)Em variáveis locais da fábrica
PrivacidadeNenhuma (só a convenção do _)De verdade: de fora, não se alcança
Chamadaconta:depositar(50), com dois-pontosconta.depositar(50), com ponto
FunçõesUma só para todos os objetos (na classe)Funções novas para cada objeto (gasta mais memória com milhares de objetos)
Herança e metamétodosNaturais (Herança, __tostring…)Possíveis, mas dão mais trabalho
Método novo depois de criar os objetosVale para todos (está na classe)Só para os objetos criados depois

Sobre as funções: no lab, duas contas da classe tinham a mesma função depositar (a.depositar == b.depositar deu true), e duas contas de closures tinham funções diferentes (false).

SituaçãoQual usar
Muitos objetos (milhares de inimigos num jogo, linhas de uma planilha)Classe com metatabela
Família de tipos (Conta → Poupança)Classe com metatabela
Poucos objetos, com regras que não podem ser furadas (saldo, senha, contador)Closures
Time pequeno que confia uns nos outrosClasse com _campo por convenção
Privacidade não é segurança

A biblioteca debug consegue espiar e até trocar as variáveis de uma closure: no lab, debug.getupvalue(ana.saldo, 1) devolveu saldo 100, e um debug.setupvalue trocou o saldo para 999. O encapsulamento protege contra enganos do seu próprio programa, não contra alguém que queira burlar de propósito. Senhas e dados sensíveis pedem outros cuidados.

Quando dá errado

Chamou a função de closure com dois-pontos 
local function nova_conta(saldo_inicial)
  local saldo = saldo_inicial
  local conta = {}
  function conta.depositar(valor)
    saldo = saldo + valor
  end
  return conta
end

local ana = nova_conta(100)
ana:depositar(50)

lua: dois_pontos.lua:5: attempt to perform arithmetic on a table value (local 'valor')

	dois_pontos.lua:11: in main chunk

O costume das classes traiu a Ana: ana:depositar(50) passou a tabela ana como primeiro argumento, que caiu em valor (a função não tem self). A soma virou "número + tabela". É o mesmo erro da aula Métodos. Como consertar: ana.depositar(50). Objetos de closures se usam com ponto.

Escreveu por cima de um "botão" 
local function nova_conta(saldo_inicial)
  local saldo = saldo_inicial
  local conta = {}
  function conta.saldo() return saldo end
  return conta
end

local ana = nova_conta(100)
ana.saldo = 0
print(ana.saldo())

$ lua sobrescreveu.lua
lua: sobrescreveu.lua:10: attempt to call a number value (field 'saldo')
stack traceback:
	sobrescreveu.lua:10: in main chunk
	[C]: in ?

O cofre continua intacto (o saldo de dentro ainda é 100), mas a tabela dos botões é uma tabela comum, e a linha 9 trocou o botão saldo pelo número 0. Na linha 10, ana.saldo() tentou chamar um número: "tentativa de chamar um valor número (o campo saldo)". Como consertar: não escreva nos campos de um objeto de closures. Se quiser impedir de vez, trave a tabela, como abaixo.

Travando a tabela dos botões com __newindex

Juntando a closure com a tabela só de leitura da aula __index e __newindex: os botões ficam numa tabela escondida (metodos), e a conta devolvida é uma tabela vazia que lê dela e recusa qualquer gravação.

local function nova_conta(saldo_inicial)
  local saldo = saldo_inicial
  local metodos = {}
  function metodos.depositar(valor) saldo = saldo + valor end
  function metodos.saldo() return saldo end
  return setmetatable({}, {
    __index = metodos,
    __newindex = function (t, chave)
      error("a conta não aceita o campo '" .. tostring(chave) .. "'", 2)
    end,
  })
end

local ana = nova_conta(100)
ana.depositar(50)
print(ana.saldo())
ana.saldo = 0

$ lua travada.lua
150
lua: travada.lua:17: a conta não aceita o campo 'saldo'
stack traceback:
	[C]: in global 'error'
	travada.lua:9: in metamethod 'newindex'
	travada.lua:17: in main chunk
	[C]: in ?

Agora o ana.saldo = 0 para o programa na hora, na linha certa, em vez de quebrar mais tarde. (O rawset ainda passaria por cima, mas isso já é burlar de propósito.)

Referência rápida: o molde de um objeto com closures

local function novo_objeto(valor_inicial)
  local dado = valor_inicial        -- privado: só as funções abaixo enxergam
  local obj = {}

  function obj.mudar(novo)          -- regras ficam aqui dentro
    if novo < 0 then error("valor inválido", 2) end
    dado = novo
  end

  function obj.ler()                -- "getter": devolve, não deixa mudar
    return dado
  end

  return obj                        -- só os botões saem da fábrica
end

local o = novo_objeto(10)
o.mudar(20)                         -- com ponto, sem self
print(o.ler())
Mensagem ou sintomaCausa provável
Erro dentro de um método certo, por causa de um campo com valor estranhoAlguém mudou o campo de fora: encapsule
attempt to perform arithmetic on a table value (local 'valor')Chamou com : uma função de closure (use .)
attempt to call a number value (field '…')Um "botão" foi sobrescrito por um valor
nil ao ler obj.dadoNão é erro: o dado é privado; use a função de leitura

Missão final: o contador que ninguém fura

Missão: o contador de visitas do site da padaria guarda o total num campo da tabela, e uma linha "espertinha" (visitas.total = 1000) inflou o número. Reescreva o novo_contador com closure: troque o campo por uma variável local total = 0 dentro da fábrica e faça as duas funções usarem essa variável. Sem mexer nas linhas de baixo, o resultado deve ser Visitas: 3.

local function novo_contador()
  local contador = { total = 0 }

  function contador.mais_um()
    contador.total = contador.total + 1
  end

  function contador.valor()
    return contador.total
  end

  return contador
end

local visitas = novo_contador()
visitas.mais_um()
visitas.mais_um()
visitas.mais_um()
visitas.total = 1000
print("Visitas: " .. visitas.valor())

local function novo_contador()
  local total = 0
  local contador = {}

  function contador.mais_um()
    total = total + 1
  end

  function contador.valor()
    return total
  end

  return contador
end

local visitas = novo_contador()
visitas.mais_um()
visitas.mais_um()
visitas.mais_um()
visitas.total = 1000
print("Visitas: " .. visitas.valor())

No lab, a versão com closure mostrou Visitas: 3: o visitas.total = 1000 só criou um campo novo e inútil na tabela, longe do total de verdade.

Resumo

  • Encapsular é deixar os dados de um objeto acessíveis só pelas funções dele. Campos abertos (conta.saldo) aceitam qualquer valor, e o erro aparece longe da causa.
  • O sublinhado (_saldo) é só uma convenção: o Lua não protege nada.
  • Com closures, o dado vira uma variável local da função fábrica; as funções criadas lá dentro são as únicas que o enxergam. De fora, ele não existe.
  • Objetos de closures se usam com ponto (ana.depositar(50)): as funções não precisam de self.
  • Entregue cópias de tabelas privadas, nunca a própria tabela.
  • Classes com metatabela: muitos objetos, herança, metamétodos. Closures: poucos objetos com regras que não podem ser furadas. As duas formas podem se juntar (closure + __newindex para travar).
