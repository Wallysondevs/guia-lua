Lua <close>

Quem abre a porta da padaria de manhã precisa fechá-la à noite. No programa é igual: quem abre um arquivo precisa fechá-lo com f:close(). O problema é que é fácil esquecer, e mais fácil ainda o programa pular o f:close() sem querer: um return no meio da função, um break, um erro. O atributo <close> ("fechar") resolve isso: você o põe na variável quando abre, e o Lua fecha sozinho quando a variável sai de cena, aconteça o que acontecer.

Você vai aprender
  • Como abrir um arquivo com local f <close> = io.open(…) e deixar o Lua fechá-lo no fim do bloco.
  • O que é o metamétodo __close e como fazer o seu próprio "recurso que se fecha".
  • Em que ordem as coisas se fecham, e que o fechamento acontece também com break, return e erro.
  • O caso do os.exit, que pode pular o fechamento.
  • As mensagens de erro reais: non-closable value, multiple to-be-closed variables e outras.

Todos os programas desta aula rodaram no Lua 5.5 da máquina da Ana (usuária ana, computador notebook), na pasta pessoal dela, com lua arquivo.lua. Você vai precisar de três aulas anteriores: <const> (o <close> é parente dele), Abrindo Arquivos e Metatabelas.

A ideia: a porta com mola

Algumas portas de loja têm uma mola: você entra, solta a porta, e ela se fecha sozinha atrás de você. Não importa se você entrou devagar, correndo ou tropeçando: a porta fecha. O <close> é essa mola. Você a "instala" na hora de criar a variável:

  • a variável vive dentro de um bloco (um do … end, o corpo de uma função, de um for, de um if, ou o arquivo inteiro);
  • quando o programa sai desse bloco, por qualquer caminho, o Lua chama o fechamento do valor guardado nela.

Os programadores chamam isso de variável "a ser fechada" (em inglês, to-be-closed variable). Você vai ver esse nome em inglês em algumas mensagens de erro.

1. Um arquivo que se fecha sozinho

A Ana grava a lista de compras num arquivo. Em vez de chamar f:close() no fim, ela põe o <close> na variável e deixa o arquivo dentro de um bloco do … end:

local guardado
do
  local f <close> = assert(io.open("lista.txt", "w"))
  f:write("pão\nleite\n")
  guardado = f
  print(io.type(guardado))
end
print(io.type(guardado))
for linha in io.lines("lista.txt") do print(linha) end
local guardado
Uma variável comum, criada fora do bloco, só para a gente espiar o arquivo depois que o bloco acabar.
do … end
Um bloco. É no end dele que a variável f deixa de existir, e é aí que o fechamento acontece.
local f <close>
A variável com a "mola". O atributo vem depois do nome, como o <const>.
assert(io.open("lista.txt", "w"))
Abre o arquivo para escrever ("w"). O assert para o programa com a mensagem do io.open se a abertura falhar (veja assert).
io.type(guardado)
Diz o que é o valor: "file" (arquivo aberto), "closed file" (arquivo fechado) ou nil (não é arquivo).
$ lua arquivo.lua
file
closed file
pão
leite

Dentro do bloco, o arquivo estava aberto (file). Logo depois do end, já estava fechado (closed file), sem nenhum f:close() no código. E como foi fechado, tudo o que foi escrito chegou ao disco: o io.lines leu as duas linhas.

Por que fechar faz diferença

O f:write não escreve no disco na mesma hora: ele junta o texto num buffer (uma área de espera na memória) e grava de vez, de tempos em tempos ou quando o arquivo é fechado. Se você lê o arquivo antes de fechá-lo, pode encontrá-lo vazio. A missão abaixo mostra isso de verdade.

Missão: a função salvar esqueceu de fechar o arquivo. Rode e veja: a lista sai vazia (só aparece Na lista: e fim da lista). Conserte com <close> na variável f: o arquivo vai se fechar quando a função terminar, antes de o programa ler a lista.

local function salvar(itens)
  local f = assert(io.open("compras.txt", "w"))
  for _, item in ipairs(itens) do
    f:write(item, "\n")
  end
end
salvar({ "pão", "leite", "café" })
print("Na lista:")
for linha in io.lines("compras.txt") do
  print("- " .. linha)
end
print("fim da lista")

local function salvar(itens)
  local f <close> = assert(io.open("compras.txt", "w"))
  for _, item in ipairs(itens) do
    f:write(item, "\n")
  end
end
salvar({ "pão", "leite", "café" })
print("Na lista:")
for linha in io.lines("compras.txt") do
  print("- " .. linha)
end
print("fim da lista")

No lab, o programa sem o <close> mostrou só Na lista: e fim da lista. Com ele, apareceram - pão, - leite e - café. Aqui o bloco é o corpo da função salvar: não precisou de do … end.

2. Por dentro: o metamétodo __close

Como o Lua sabe como fechar um arquivo? Ele procura, na metatabela do valor, um campo chamado __close, e o chama. Os arquivos do Lua já vêm com esse campo. E você pode dar um __close às suas próprias tabelas:

local function recurso(nome)
  return setmetatable({ nome = nome }, {
    __close = function (r, erro)
      print("fechando " .. r.nome)
    end
  })
end
print("antes do bloco")
do
  local porta <close> = recurso("porta")
  print("usando a " .. porta.nome)
end
print("depois do bloco")
recurso(nome)
Uma função que cria uma tabela { nome = … } com uma metatabela. É a nossa "porta de mentirinha".
__close = function (r, erro)
O fechamento. O Lua chama essa função passando o próprio valor (r) e, se o bloco terminou por causa de um erro, o erro (erro). Se não houve erro, o segundo argumento não vem (fica nil).
local porta <close> = recurso("porta")
A variável com a mola. Quando o do … end acabar, o Lua chama o __close da tabela que está em porta.
$ lua primeiro.lua
antes do bloco
usando a porta
fechando porta
depois do bloco

O fechando porta apareceu exatamente entre o fim do bloco e a linha seguinte. Você não chamou o __close em lugar nenhum: o end chamou.

Vários ao mesmo tempo: do último para o primeiro

local function recurso(nome)
  print("abrindo " .. nome)
  return setmetatable({ nome = nome }, {
    __close = function (r) print("fechando " .. r.nome) end
  })
end
do
  local a <close> = recurso("forno")
  local b <close> = recurso("caixa")
  local c <close> = recurso("porta")
  print("padaria funcionando")
end

$ lua ordem.lua
abrindo forno
abrindo caixa
abrindo porta
padaria funcionando
fechando porta
fechando caixa
fechando forno

Fecha na ordem contrária à de abertura, como um padeiro de verdade: o último a abrir foi a porta, e ela é a primeira a fechar; o forno, ligado primeiro, é desligado por último. Isso é importante quando uma coisa depende da outra (um arquivo aberto dentro de uma pasta temporária, por exemplo: feche o arquivo antes de apagar a pasta).

Experimente: crie mais um recurso, local d <close> = recurso("luz"), entre o forno e a caixa. Antes de rodar, tente adivinhar em que linha da saída aparece o fechando luz.

local function recurso(nome)
  print("abrindo " .. nome)
  return setmetatable({ nome = nome }, {
    __close = function (r) print("fechando " .. r.nome) end
  })
end
do
  local a <close> = recurso("forno")
  local b <close> = recurso("caixa")
  local c <close> = recurso("porta")
  print("padaria funcionando")
end

3. Fecha por qualquer saída: break, return e erro

Esta é a grande vantagem sobre o f:close() escrito à mão. O mesmo recurso, agora mostrando também o segundo argumento do __close (o erro):

local function recurso(nome)
  return setmetatable({ nome = nome }, {
    __close = function (r, erro) print("  fechando " .. r.nome, erro) end
  })
end
for i = 1, 3 do
  local r <close> = recurso("volta " .. i)
  if i == 2 then print("break!") break end
  print("fim da volta " .. i)
end
local function f()
  local r <close> = recurso("função")
  print("return!")
  return "resultado"
end
print(f())
print(pcall(function ()
  local r <close> = recurso("com erro")
  error("o forno queimou")
end))

$ lua saidas.lua
fim da volta 1
  fechando volta 1	nil
break!
  fechando volta 2	nil
return!
  fechando função	nil
resultado
  fechando com erro	saidas.lua:19: o forno queimou
false	saidas.lua:19: o forno queimou

Cada caso:

  • Fim normal de cada volta do for: o corpo do laço é um bloco, então a cada volta o recurso daquela volta se fecha (fechando volta 1).
  • break: na volta 2, o programa saiu do laço no meio, e mesmo assim fechando volta 2 apareceu. A volta 3 nem começou.
  • return: a função ia devolver "resultado"; antes de o valor chegar ao print, o recurso dela se fechou.
  • Erro: o error("o forno queimou") interrompeu a função, e o __close rodou recebendo o erro no segundo argumento. Depois, o erro continuou seu caminho até o pcall, que devolveu false e a mensagem (veja pcall).

Nos três primeiros casos o segundo argumento é nil: não houve erro.

E se ninguém tratar o erro?

Mesmo quando o erro vai derrubar o programa, o fechamento acontece antes:

local r <close> = setmetatable({}, { __close = function (_, e) print("fechou! erro:", e) end })
local t = nil
print(t.x)

$ lua erro_nao_tratado.lua
fechou! erro:	erro_nao_tratado.lua:3: attempt to index a nil value (local 't')
stack traceback:
	erro_nao_tratado.lua:3: in main chunk
	[C]: in ?
lua: erro_nao_tratado.lua:3: attempt to index a nil value (local 't')
stack traceback:
	erro_nao_tratado.lua:3: in main chunk
	[C]: in ?

Aqui a variável r está no arquivo inteiro (o arquivo também é um bloco). O erro da linha 3 encerrou esse bloco, então o __close rodou e mostrou fechou! erro:, seguido do erro. A mensagem aparece duas vezes: a primeira é o print do nosso __close; a segunda, com o lua: na frente, é o próprio lua avisando que o programa parou. (O erro que o __close recebeu já veio com o stack traceback grudado: quando ninguém trata o erro, o lua monta o rastro antes de desfazer os blocos.)

O cuidado com o os.exit

local r <close> = setmetatable({}, { __close = function () print("fechou!") end })
print("saindo")
os.exit(0)

$ lua exit.lua
saindo

Nada de fechou!. O os.exit(0) encerra o programa na hora, sem desfazer os blocos. Para ele fechar tudo antes de sair, passe true como segundo argumento (veja os.exit):

$ cat exit2.lua
local r <close> = setmetatable({}, { __close = function () print("fechou!") end })
print("saindo")
os.exit(0, true)
$ lua exit2.lua
saindo
fechou!

Quando o programa termina normalmente, na última linha, também fecha: com o mesmo r e só um print("última linha"), o lab mostrou última linha e depois fechou!.

4. Quando a abertura falha: nil é aceito

O manual do Lua diz que uma variável <close> pode receber nil ou false: nesse caso, não há o que fechar, e o Lua simplesmente ignora. Isso combina com o io.open, que devolve nil quando não consegue abrir:

local f <close> = io.open("nao_existe.txt")
print(f)

$ lua naoexiste.lua
nil

Sem erro na linha 1. Mas o programa precisa conferir o f antes de usá-lo (ou usar o assert, como na seção 1). Qualquer outro valor sem __close (uma tabela comum, um número, um texto) é erro: veja em Quando dá errado.

Formas diferentes de fazer a mesma coisa

Três jeitos de garantir que um arquivo seja fechado:

-- 1) à mão: funciona, se nada pular o close
local f1 = assert(io.open("a.txt", "w"))
f1:write("oi\n")
f1:close()

-- 2) com <close> num bloco
do
  local f2 <close> = assert(io.open("b.txt", "w"))
  f2:write("oi\n")
end

-- 3) io.lines, que abre e fecha sozinho quando a leitura termina
for linha in io.lines("a.txt") do print(linha) end
SituaçãoQual usar
Ler um arquivo linha por linha, do começo ao fimio.lines (aula io.lines)
Escrever ou ler num trecho com return, break ou risco de erro no meiolocal f <close> = …
Um programa curto, sem desvios, que precisa rodar também no Lua 5.1/LuaJITf:close() à mão
Um recurso seu (uma conexão, um cronômetro, um "trava/destrava")Uma tabela com __close e <close>
E nas outras versões?

O <close> surgiu no Lua 5.4; o ordem.lua deu a mesma saída no lua5.4 do lab. No Lua 5.1 e no LuaJIT não existe: luajit ordem.lua → luajit: ordem.lua:8: unexpected symbol near '<'. Lá, feche à mão (e use pcall para garantir o fechamento quando houver erro). Veja as diferenças entre as versões.

Quando dá errado

O valor não sabe se fechar 
local x <close> = { nome = "porta" }
print("chegou aqui?")

$ lua semclose.lua
lua: semclose.lua:1: variable 'x' got a non-closable value
stack traceback:
	semclose.lua:1: in main chunk
	[C]: in ?

"A variável 'x' recebeu um valor que não pode ser fechado". A tabela não tem metatabela com __close, e então o Lua não saberia o que fazer no fim do bloco. Ele reclama logo na linha 1, ao rodar (repare no stack traceback: é um erro de execução, e o chegou aqui? não aparece). Com um número (local x <close> = 42), a mensagem é a mesma. Como consertar: só use <close> com arquivos, com tabelas que tenham __close ou com nil/false.

Tentou trocar o valor da variável 
local f <close> = io.open("lista.txt")
f = nil

$ lua atribuir.lua
lua: atribuir.lua:2: attempt to assign to const variable 'f'

Uma variável <close> também é constante: ela tem de continuar com o mesmo valor até o fim, para o Lua saber o que fechar. A mensagem é a mesma da aula <const>, e também sai antes de o programa rodar.

Dois <close> na mesma linha 
local a <close>, b <close> = io.open("lista.txt"), io.open("lista.txt")

$ lua dois.lua
lua: dois.lua:1: multiple to-be-closed variables in local list

"Várias variáveis a serem fechadas na mesma lista de local". O Lua só aceita uma por linha. Como consertar: uma linha para cada: local a <close> = … e, embaixo, local b <close> = ….

Tentou com uma variável global 
global x <close> = io.open("lista.txt")

$ lua global.lua
lua: global.lua:1: global variables cannot be to-be-closed

"Variáveis globais não podem ser a serem fechadas". Só variáveis local têm <close>: uma global não tem um bloco onde "acabar". (A palavra global é do Lua 5.5; veja A Declaração global.)

Erro dentro do próprio __close 
local r <close> = setmetatable({}, {
  __close = function () error("deu ruim ao fechar") end
})
print("usando")

$ lua erroclose.lua
usando
lua: erroclose.lua:2: deu ruim ao fechar
stack traceback:
	[C]: in global 'error'
	erroclose.lua:2: in metamethod 'close'
	erroclose.lua:4: in main chunk
	[C]: in ?

O programa rodou até o fim (usando), e o erro aconteceu na hora de fechar. O rastro conta isso: in metamethod 'close' ("no metamétodo close") mostra que o erro estava dentro do __close. Um erro ali é tratado como um erro comum do bloco. Se houver outros <close> pendentes, o manual garante que eles ainda são fechados.

Missão final: o cronômetro da fornada

Missão: a função fornada tem um return no meio, quando o pão queima, e por isso o encerrar(forno) do fim nunca roda (o lab mostrou só forno ligado e pão queimou!). Dê ao forno uma metatabela com __close que mostre fornada encerrada, guarde-o numa variável <close> e apague a chamada a encerrar.

local function encerrar(forno)
  print("fornada encerrada")
end
local function fornada(minutos)
  local forno = { temperatura = 200 }
  print("forno ligado")
  if minutos > 30 then
    print("pão queimou!")
    return false
  end
  print("pão pronto")
  encerrar(forno)
  return true
end
fornada(40)

local function fornada(minutos)
  local forno <close> = setmetatable({ temperatura = 200 }, {
    __close = function () print("fornada encerrada") end
  })
  print("forno ligado")
  if minutos > 30 then
    print("pão queimou!")
    return false
  end
  print("pão pronto")
  return true
end
fornada(40)

Resumo

  • local x <close> = valor faz o Lua chamar o __close do valor quando o bloco da variável termina, por qualquer caminho: fim normal, break, return ou erro.
  • Arquivos já têm __close: local f <close> = assert(io.open(…)) fecha sozinho. Para os seus valores, ponha __close na metatabela.
  • O __close recebe o valor e, se houve erro, o erro. Vários fecham do último para o primeiro.
  • nil e false são aceitos (nada a fechar); outros valores sem __close dão non-closable value.
  • A variável <close> é constante, só local, e só uma por linha. os.exit(0) pula o fechamento; os.exit(0, true), não.
  • Existe desde o Lua 5.4; não existe no 5.1 nem no LuaJIT.
