Lua Condições Aninhadas

Dentro do bloco de um if pode ir qualquer coisa: um print, uma conta, uma variável nova… e também outro if. Isso se chama condição aninhada (como as bonecas russas, uma dentro da outra). Ela serve para as perguntas que só fazem sentido depois de outra: só vale a pena conferir a senha se o usuário existir; só vale a pena calcular o total se o produto estiver no estoque.

Você vai aprender
  • Como pôr um if dentro de outro, e como o Lua decide qual else e qual end pertencem a qual if.
  • Dois exemplos completos: o login (usuário e senha) e a venda (estoque, quantidade e saldo).
  • Como o aninhado protege contra erros: testar se um valor existe antes de comparar.
  • Quando trocar o aninhado por and ou por elseif, e quando não dá.
  • Por que a indentação é tão importante aqui: ela pode mentir para quem lê.
  • Os erros reais do end que falta no if de dentro.

Todos os programas desta aula rodaram no Lua 5.5 da máquina da Ana (usuária ana, computador notebook), com lua arquivo.lua. Você pode rodar cada um no editor do guia.

A ideia: o porteiro do prédio

A Ana mora num prédio com porteiro. Quando alguém chega, ele pensa assim:

  1. Essa pessoa mora aqui (está no cadastro)?
    • Sim → então eu pergunto a senha da portaria. A senha está certa?
      • Sim → libero a entrada.
      • Não → "Senha errada".
    • Não → "Não encontrei esse nome", e nem pergunto a senha.

A segunda pergunta (a senha) fica dentro do "sim" da primeira. Para quem não mora no prédio, ela nem é feita. No código, isso vira um if dentro do bloco de outro if.

Como o Lua sabe qual end é de qual if?

Pela ordem, não pelos espaços. Cada end (e cada else) pertence ao if mais próximo que ainda está aberto. Por isso o primeiro end fecha o if de dentro: ele foi o último a abrir. É como empilhar pratos: o último que você põe é o primeiro que você tira.

2. Três níveis: a venda da lojinha

Dá para aninhar mais de um nível. Na lojinha da Ana, para vender é preciso: ter o produto; ter a quantidade pedida; e o cliente ter saldo para o total. Cada pergunta só faz sentido se a anterior deu "sim":

local estoque = 4
local quantidade = 6
local saldo = 100
local preco = 12

if estoque > 0 then
  print("Temos o produto.")
  if quantidade <= estoque then
    local total = quantidade * preco
    if saldo >= total then
      print("Venda feita: R$ " .. total)
    else
      print("Saldo insuficiente para R$ " .. total)
    end
  else
    print("Só temos " .. estoque .. " unidades.")
  end
else
  print("Produto esgotado.")
end

$ lua venda.lua
Temos o produto.
Só temos 4 unidades.

O cliente pediu 6 e só havia 4: a segunda pergunta deu "não", e o programa nem calculou o total. A Ana trocou os valores e rodou de novo (cada linha $ abaixo é uma versão do programa com os valores do comentário):

$ lua venda.lua                « quantidade = 3
Temos o produto.
Venda feita: R$ 36
$ lua venda.lua                « quantidade = 3, saldo = 20
Temos o produto.
Saldo insuficiente para R$ 36
$ lua venda.lua                « estoque = 0
Produto esgotado.

Repare na local total: ela foi criada dentro do segundo nível, porque só ali ela é necessária. Ela existe nesse bloco e no if de dentro dele (que é parte do bloco), e some no end que o fecha. Com três níveis, os 2 espaços por nível fazem toda a diferença para enxergar o que está dentro de quê.

3. Testar se existe antes de comparar

Um uso muito comum do aninhado: proteger uma comparação. O tonumber devolve nil quando o texto não é um número, e comparar nil com um número dá erro:

local texto = "abc"
local n = tonumber(texto)
if n > 0 then
  print("positivo")
end

$ lua numero.lua
lua: numero.lua:3: attempt to compare number with nil
stack traceback:
	numero.lua:3: in main chunk
	[C]: in ?

A solução é perguntar primeiro se o número existe e, só dentro do "sim", comparar:

local texto = "abc"
local n = tonumber(texto)
if n then
  if n > 0 then
    print(n .. " é positivo")
  else
    print(n .. " não é positivo")
  end
else
  print("'" .. texto .. "' não é um número")
end

$ lua numero2.lua
'abc' não é um número

Com texto = "5", saiu 5 é positivo; com "-2", -2 não é positivo. O if n > 0 agora só roda quando n é um número de verdade.

Experimente: troque o texto por "5", "-2", "0", "3.7", "" (vazio) e "10 reais". Qual dos três blocos roda em cada caso?

Formas diferentes de fazer a mesma coisa

Quando o aninhado vira um and

Se o if de dentro e o de fora não têm else, as duas perguntas podem virar uma só, com and (veja and, or e not):

local idade = 20
local tem_titulo = true

-- aninhado
if idade >= 18 then
  if tem_titulo then
    print("Pode votar (aninhado).")
  end
end

-- com and
if idade >= 18 and tem_titulo then
  print("Pode votar (and).")
end

$ lua comand.lua
Pode votar (aninhado).
Pode votar (and).

Os dois fazem o mesmo, e o do and é mais curto. Ele também é seguro para a proteção da seção 3: o and só olha o lado direito se o esquerdo for verdadeiro, então if n and n > 0 then nunca compara um nil.

Quando não dá para usar and

Se cada "não" precisa de uma resposta diferente, o and perde informação. Aqui cada situação tem a sua mensagem:

local idade = 20
local tem_titulo = false

if idade >= 18 then
  if tem_titulo then
    print("Pode votar.")
  else
    print("Tem idade, mas precisa tirar o título.")
  end
else
  print("Ainda não tem idade para votar.")
end

$ lua mensagens.lua
Tem idade, mas precisa tirar o título.

Com if idade >= 18 and tem_titulo then … else … end, o else não saberia dizer qual das duas condições falhou.

Quando o aninhado vira um elseif

Se o if de dentro é a única coisa dentro de um else, ele pode virar um elseif (veja elseif). Estas duas formas são iguais:

Aninhado (dois end)Com elseif (um end)
if nota >= 7 then
  print("aprovada")
else
  if nota >= 5 then
    print("recuperação")
  else
    print("reprovada")
  end
end

if nota >= 7 then
  print("aprovada")
elseif nota >= 5 then
  print("recuperação")
else
  print("reprovada")
end

A segunda pergunta só faz sentido depois da primeira, e cada "não" tem a sua respostaif dentro de if

4. A indentação que mente

O Lua não olha os espaços: quem decide de quem é cada else e cada end é a ordem. Então uma indentação errada pode enganar quem lê. Olhe este programa com atenção:

local tem_cadastro = false
local senha_certa = false

if tem_cadastro then
  if senha_certa then
    print("Entrou.")
else
  print("Usuário não encontrado.")
  end
end
print("fim")

Pelo jeito como está escrito, parece que o else é do if tem_cadastro (estão alinhados). Então, com tem_cadastro = false, deveria aparecer Usuário não encontrado.. Mas:

$ lua mentira.lua
fim

Na hora do else, o if mais próximo ainda aberto é o if senha_certa: o else é dele. E com tem_cadastro = true (e a senha errada) a mensagem aparece no caso errado:

$ lua mentira.lua                « tem_cadastro = true
Usuário não encontrado.
fim

O Lua não deu erro nenhum: o programa é válido, só não faz o que a indentação sugere. Indentado do jeito que o Lua o enxerga, o problema salta aos olhos:

if tem_cadastro then
  if senha_certa then
    print("Entrou.")
  else
    print("Usuário não encontrado.")
  end
end
Deixe o editor de texto indentar por você

Editores de código (VS Code, Neovim, ZeroBrane Studio…) têm um comando para reindentar o arquivo de acordo com os if/end de verdade. Use-o quando a lógica parecer não bater com o que você lê: se as linhas "pularem" de lugar, achou o problema.

Quando dá errado

Faltou o end do if de dentro 
local usuario = "ana"
local senha = "pao123"

if usuario == "ana" then
  if senha == "pao123" then
    print("Bem-vinda, Ana!")
  else
    print("Senha errada.")

  print("Usuário não encontrado.")
end

$ lua faltaend.lua
lua: faltaend.lua:9: 'end' expected (to close 'if' at line 5) near 'else'
faltaend.lua:9:
A linha 9, a do segundo else.
'end' expected (to close 'if' at line 5)
"Era esperado um end para fechar o if da linha 5": o if de dentro (o da senha).
near 'else'
O if de dentro já tinha um else (linha 7). Quando veio outro else, ainda com ele aberto, o Lua entendeu que estava faltando o end antes.

Desta vez a mensagem aponta quase o lugar exato. Como consertar: ponha o end na linha 9, antes do segundo else, alinhado com o if senha ….

Faltou um end no fim 
local usuario = "ana"
local senha = "pao123"

if usuario == "ana" then
  if senha == "pao123" then
    print("Bem-vinda, Ana!")
  end

$ lua faltaend2.lua
lua: faltaend2.lua:8: 'end' expected (to close 'if' at line 4) near <eof>

O único end fechou o if de dentro (o mais recente); o de fora, da linha 4, chegou aberto ao fim do arquivo. Como consertar: mais um end no fim. A regra para conferir: conte os ifs (sem contar os elseif) e os ends. Os números têm de bater.

Comparou antes de testar se existe

É o erro da seção 3: attempt to compare number with nil. Ele aparece quando uma variável que pode ser nil (o resultado do tonumber, do io.read() no fim da entrada, um nome digitado errado) entra numa comparação com <, >, <= ou >=. Como consertar: teste primeiro (if n then) e compare dentro, ou junte as duas com if n and n > 0 then.

O else foi parar no if errado

É o caso da seção 4: nenhuma mensagem de erro, mas a resposta aparece na situação errada (ou não aparece). Como achar: reindente o código seguindo a regra "cada else e cada end é do if aberto mais recente" e veja se ficou como você queria.

Resumo

  • Um if pode ter outro if dentro do seu bloco: é a condição aninhada, para perguntas que só fazem sentido depois de outra.
  • Cada else e cada end pertence ao if aberto mais recente. Os espaços não contam para o Lua, mas indentar 2 espaços por nível evita que o código "minta" para quem lê.
  • Um end por if. O erro 'end' expected (to close 'if' at line N) diz qual ficou aberto.
  • Teste se um valor existe antes de compará-lo: if n then if n > 0 … ou if n and n > 0 then.
  • Sem else, dois ifs aninhados viram if a and b then. Um if sozinho dentro de um else vira elseif.
